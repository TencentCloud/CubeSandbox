# cube-envd SDK 性能报告

[English](performance.md) · [组件概览](../README_zh.md) · [功能验证](validation_zh.md)

## 修复后 Rust 的性能

本次测量针对现有功能分支开发过程中的 Rust 性能修复。入站连接启用 `TCP_NODELAY` 后，Rust 的 SDK **短命令 median
为 14.348 ms，4 KiB 读取为 1.813 ms**；Go 对照分别为 16.026 ms 和 1.451 ms。
本轮 Rust 大文件读取也快于 Go；小文件操作总体仍由 Go 领先，大文件写入差距仍然明显。

下文“Rust（修复后）”指包含本次修改的实测实现，不是另一个发布版本。
修复前后列用于说明 Rust 开发过程中的改善，不预设 Rust 必须快于 Go。
Go 仍为默认 provider，Rust 仍需显式选择。

## 对比结果

延迟单位为毫秒。每个实现、每个场景共有 **500 个正式成功样本、0 个错误**，
分布在五组独立测量中。变化率为 `(修复后 / 对照 - 1) × 100`，负数表示延迟降低。
总体 median 和 nearest-rank p95 是合并样本的描述性统计；是否稳定改善，需结合
下方的逐组结果判断。

| 场景 | Rust（修复后）median / p95 | Go median / p95 | Rust（修复前）median / p95 | 修复后相对 Go 的 median 变化 | 修复后相对修复前的 median 变化 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 短命令 | 14.348 / 16.212 | 16.026 / 18.434 | 47.892 / 49.041 | -10.47% | -70.04% |
| 4 KiB 读 | 1.813 / 2.540 | 1.451 / 2.547 | 44.093 / 45.592 | +24.95% | -95.89% |
| 4 KiB 写 | 1.475 / 2.056 | 1.319 / 2.022 | 2.404 / 3.190 | +11.84% | -38.63% |
| 4 MiB 读 | 26.965 / 31.779 | 33.636 / 39.172 | 58.065 / 62.825 | -19.83% | -53.56% |
| 4 MiB 写 | 31.493 / 36.815 | 12.764 / 16.976 | 32.144 / 36.625 | +146.74% | -2.03% |

短命令、小文件读写及大文件读取，相对修复前 Rust 均在全部五组改善。
4 KiB 读取 median 降低 95.40%–96.05%，短命令降低 68.18%–72.01%。
大文件写入的 median 变化很小，四组降低、一组升高；p95 在第 1–3 组升高、
第 4–5 组降低，**不宣称取得稳定的大文件上传改善**。修复后 4 MiB 写入 median
仍约为 Go 的 2.47 倍；4 KiB 读取仍比 Go 慢约 25%。

## 测量方法

复用现有 [SDK 性能用例](../../tests/e2e/sdk_compat/cases/performance/test_envd_comparison.py)、
[计时与统计辅助函数](../../tests/e2e/sdk_compat/framework/envd_performance.py)及
[模板与 sandbox 验收辅助函数](../../tests/e2e/sdk_compat/framework/envd_acceptance.py)。
请求全部经过原 SDK/CubeProxy 路径，没有直连 guest 绕过代理。

- 五组测量，每组为 Go、修复前 Rust、修复后 Rust 分别创建新 sandbox，共 15 个。
  第 1/3/5 组按 Go → 修复前 → 修复后执行，第 2/4 组反向执行。
  每个 sandbox 创建、测量、清理后再处理下一个，测量时仅驻留一个 sandbox。
- 并发为 1。每个 sandbox、每个场景分别记录首次调用 1 次、预热 5 次、正式样本
  100 次。“首次”是身份/健康检查之后的首次场景调用，不代表 daemon 冷启动。
- 场景顺序为 `printf 'envd-perf'`、4 KiB 写/读、4 MiB 写/读，文件分别为
  4096 和 4194304 字节。命令必须返回完整 stdout、空 stderr 和退出码 0。
  写入通过计时外的完整 SDK 读回校验；读取计时包含 SDK 完整消费响应。
- 使用 `perf_counter_ns` 计时；结果记录序列化、校验、创建与清理在计时外。SDK 重试和
  返回消费方式不变，不增加操作重试，不用补测替换失败。时间包含 SDK 内部行为，
  但没有另行观测其内部重试次数。
- median 使用 `statistics.median`；p95 为成功样本排序后的 `ceil(0.95 × n)` 位。
  错误单独报告。总体统计不是各组 median 的平均值，也不是生产尾延迟保证。

完整测量共 **7,950 次成功操作**：首次 75 次、预热 375 次、正式样本 7,500 次；
**操作错误为 0，18 项清理记录无错误**（15 个 sandbox、3 个模板）。此前一次尝试
同时驻留三个 sandbox，在平台重置 guest 时间时失败，尚未取得样本；该失败不计入
上述成功数。清理失败运行时后，对所有实现统一改为依次创建、测量、清理，并完整重跑。

正式测量期间停止构建、抓包及无关虚拟机，必要平台服务继续运行。
296 个宿主监控样本的 CPU idle 最小/中位/最大值为 53/78/97%；swap-in 中位数为
44 KiB/s、最大 10,924 KiB/s，iowait 最大 9%。这不是无噪声的专用测试机器，
小幅差异和尾部统计需要在这一条件下解读。

## 连接修改为何有效

本次修改为每个入站 HTTP socket 启用 `TCP_NODELAY`，禁用 Nagle 缓冲，使小块流式正文及进程结束
事件无需等待前一段响应的 ACK 即可发送。空闲连接跟踪、认证、用户权限、输出与
退出语义、cgroup 初始化降级均保持。设置选项失败时记录警告，保留可用连接。

独立诊断抓包支持这一机制：一次修复前 4 KiB 读取中，guest 收到请求后 2.413 ms
即发出首段 212 字节，随后等待代理 ACK 40.739 ms，剩余 39 字节在 ACK 后
0.186 ms 发出。修复后示例的首段准备耗时为 1.026 ms，剩余 39 字节仅隔
0.024 ms 就发出，**早于 ACK**。短命令的修复前抓包也显示约 40 ms 的同类等待。
认证、路由和文件系统操作耗时包含在首段响应前的时间内，未进一步单独 profiling。
诊断时间不计入正式样本。首次修复后抓包不完整，随后重新采集；完整复采记录
501/501 个包，内核丢包为 0。

## CPU、内存与并发

独立资源检查为每种 Rust 实现创建三个独立 sandbox，交替实现顺序，在并发 1 和 4
下每场景、每窗口执行 40 次带校验操作：**2,400 成功、0 错误**。
CPU 使用 daemon 的用户态/内核态 tick 差值，包含控制调用与写入读回校验，不含
命令子进程，且受 guest 时钟粒度限制。VmHWM 为 daemon 累计峰值 RSS，不是整 VM
内存。本轮两种实现的最大 VmHWM 均为 3,972 KiB；修复后每操作 CPU 相当或更低。

未限制请求间隔的并发 4 检查中，修复后的**单独写入延迟有所升高**：

| 场景 | 修复前 median / p95 ms | 修复后 median / p95 ms |
| --- | ---: | ---: |
| 4 KiB 写 | 2.682 / 5.540 | 4.435 / 7.541 |
| 4 MiB 写 | 74.538 / 117.309 | 76.675 / 120.160 |

每次写入之后都有计时外读回校验，修复后读回加速提高了请求密度：40 次小文件写入
并读回的批次耗时，从修复前 0.475–0.480 s 降至修复后 0.080–0.099 s。
因此这里单独的写延迟并非相同请求到达速率下的比较。大文件写入并校验的总批次耗时
也在三组中全部缩短，尽管单独写延迟上升。

保留上述不利结果后，补充相同到达速率的诊断：三个实现配对组，每个 sandbox、每种
文件大小发送 40 批、每批四个同时发起的请求；4 KiB 批次间隔 100 ms，4 MiB 为
250 ms，共 **1,920 成功、0 错误**。该诊断不替代正式对比或未限速的资源检查。

| 场景 | 修复前 median / p95 ms | 修复后 median / p95 ms | 修复前 / 后 daemon CPU ms/操作 | 修复前 / 后峰值 VmHWM KiB |
| --- | ---: | ---: | ---: | ---: |
| 4 KiB 写 | 5.768 / 9.327 | 5.749 / 8.635 | 1.375 / 1.437 | 1780 / 1776 |
| 4 MiB 写 | 100.026 / 131.678 | 102.932 / 131.086 | 29.375 / 29.812 | 4752 / 4676 |

同到达速率下，没有一致的 p95 恶化或资源暴涨。大文件写入三组 median 变化分别为
+5.8%、-1.3%、+5.0%，p95 为 +2.0%、-1.1%、-1.7%。这些混合结果不证明上传并发
扩展能力改善，也不代表所有并发请求延迟均降低。

## 功能检查与适用范围

受测修改通过完整隔离组件检查：fmt、Clippy、build、check；**185 项 Rust 测试
通过，3 项 VM fixture ignored**。内嵌 Python 场景 6/6 通过，guest 场景 9 项通过、
1 项 IPv6 skip；后两者属于嵌套检查，不作为额外独立 Rust 测试相加。
amd64 生产基础镜像与 supervisor 测试 18/18 通过。现有公开 SDK 验收中，Go 与
修复后 Rust 各三个独立场景通过，Rust 新模板完整链也通过。Standards 与 Spec
独立审查均无阻断问题。组件/镜像测试保留源码只读、私有 cgroup，并在测试 daemon
启动前移除 SYS_TIME。

未认证原生 ARM、Firecracker 或远端 CI 的性能。结果不覆盖冷缓存存储、任意内容、
持续生产容量或全部 SDK 功能。大文件上传处理仍有优化空间，当前修改不构成引入
依赖 fork、缓存或重写线程池的依据。

## 复跑方式

使用仓库内的[构建说明](../README_zh.md#构建组件)、[模板与 SDK 指南](usage_zh.md)
以及 [SDK E2E 说明](../../tests/e2e/sdk_compat/README_zh.md)。现有显式启用的性能入口

要复跑本文设计，应构建指定 Go 对照与修复前后 Rust，对齐运行时软件包和资源，
在同一现有用例上将 provider 列表和采样循环扩展为上文五组/100 样本的安排，
并统计三个实现及全部五组。保留现有 `measure` 辅助函数、SDK 操作、完整消费、
写入读回及失败处理。分别保存首次/预热/正式样本、运行中构建身份、宿主负载和清理
结果；追踪与资源实验独立运行。本文表格直接提供报告结果，不要求访问特定机器的
文件；复跑应保留自身的原始证据，并与本轮对比分开报告。
