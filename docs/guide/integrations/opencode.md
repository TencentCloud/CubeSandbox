# OpenCode Integration Guide

This guide shows how to run [OpenCode](https://opencode.ai/docs/) in a Cube Sandbox microVM. It covers a reproducible template, sensitive configuration, network egress, and pause/resume state persistence.

## Integration Target and Version

- Target: OpenCode terminal coding agent
- Tested flow: `opencode run` in non-interactive CLI mode
- Install method: `npm install -g opencode-ai`
- Cube API: E2B-compatible Python SDK (`e2b-code-interpreter`)

The example lives in `examples/opencode-integration/`.

## Prerequisites

- A running Cube Sandbox deployment and a reachable CubeAPI endpoint, for example `http://<node-ip>:3000`
- `cubemastercli` access for template creation
- Python 3.8+ on the client machine
- An OpenCode-supported LLM provider key, such as `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, or another provider configured by OpenCode

## Build the OpenCode Template

Build and publish the template image from the example directory:

```bash
cd examples/opencode-integration
./build-template.sh
```

The script prints a `template_id`. Put it in `CUBE_TEMPLATE_ID`.

The template installs Node.js, Git, common build tools, and `opencode-ai`. It also creates `/workspace`, which is the default working directory used by the sample runner.

## Configure Secrets

Copy the environment file:

```bash
cp examples/opencode-integration/.env.example examples/opencode-integration/.env
```

Fill in:

```bash
export E2B_API_URL="http://<cube-api-host>:3000"
export E2B_API_KEY="e2b_000000"
export CUBE_TEMPLATE_ID="<template-id>"
export OPENAI_API_KEY="<provider-key>"
export OPENCODE_MODEL="openai/gpt-4.1-mini"
```

Do not bake provider API keys into images. Inject them at sandbox creation time through environment variables or write a provider config file from an encrypted secret store after the sandbox starts.

## Network and Egress

OpenCode needs outbound access to the selected LLM provider and, for many coding tasks, GitHub or package registries. Start with an allowlist that includes only the domains or CIDR ranges required by your provider and package ecosystem.

For an air-gapped code execution stage, use Cube network policies to disable public internet and run only deterministic commands generated by a previous OpenCode planning stage.

## Run the Example

```bash
cd examples/opencode-integration
pip install -r requirements.txt
python run_opencode.py --prompt "Inspect /workspace and create a short project summary."
```

The script creates a sandbox, uploads a small sample project, runs OpenCode in non-interactive mode, and prints the command output.

## Session Persistence

For short tasks, delete the sandbox when the command finishes. For long tasks, snapshot the sandbox after OpenCode has initialized its project state:

```bash
python run_opencode.py --prompt "Run /init and summarize this project." --snapshot
```

The script prints a snapshot ID. Use it as the next `template` value to resume from the same filesystem state:

```bash
python run_opencode.py --template <snapshot-id> --prompt "Continue from the previous state and run tests."
```

This pattern preserves `/workspace`, generated `AGENTS.md`, dependency caches, and OpenCode session data that lives in the sandbox filesystem.

## Typical Patterns

- Run OpenCode itself inside Cube Sandbox for isolated repository edits.
- Use a coordinator service outside Cube Sandbox to create a sandbox per task, inject secrets, run `opencode run`, collect diffs, and destroy the sandbox.
- Split planning and execution: allow egress during planning, snapshot the sandbox, then resume with stricter network policy for deterministic tests.
- Use snapshots for long-running tasks that need dependency installation or large repository checkout before the actual coding iteration.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `Template not found` | Wrong `CUBE_TEMPLATE_ID` | Run `cubemastercli tpl list` and update `.env` |
| OpenCode cannot call the model | Missing provider key or blocked egress | Check `OPENAI_API_KEY`/provider env and allow outbound access to the provider endpoint |
| `opencode: command not found` | Template was not built from the OpenCode Dockerfile | Re-run `./build-template.sh` and use the new template ID |
| Package install hangs | Registry egress blocked | Allow npm/GitHub endpoints or pre-bake dependencies into the template |
| Snapshot resume loses state | Snapshot ID was not reused as `template` | Pass `--template <snapshot-id>` or set `CUBE_TEMPLATE_ID` to the snapshot ID |
