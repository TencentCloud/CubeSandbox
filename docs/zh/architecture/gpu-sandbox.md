# GPU 沙箱设计提案（初始草案）

本文档是 Cube Sandbox 中 GPU 沙箱能力的初始设计提案。

本文档仅用于设计讨论，不代表当前版本的交付承诺、兼容性保证或实现承诺。

## 背景动机

Cube Sandbox 当前主要面向 CPU 型沙箱工作负载。越来越多的 AI 和媒体处理场景需要直接访问加速器，尤其是 NVIDIA GPU，同时仍需保持基于 MicroVM 沙箱的隔离性和生命周期控制能力。

当前工作的直接目标，是先定义一套系统设计，使 GPU 沙箱可以在不削弱现有安全模型和运维模型的前提下落地。同时，这套设计也不能把项目限制在 GPU 场景中，而应为未来扩展到 TPU 或 XPU 等其他加速器保留空间。

## 目标场景

- 运行需要一个或多个物理 GPU 的沙箱，用于推理、模型服务或媒体处理。
- 在 Cube 集群中调度 GPU 工作负载，并在沙箱生命周期内提供明确的设备独占关系。
- 通过基于 VFIO 的设备透传，将 GPU 挂载到 MicroVM。
- 支持依赖 NVIDIA 内核模块、用户态驱动库和 CUDA 工具链的 guest 软件栈。
- 为未来扩展到其他 PCIe 加速器提供设计基础。

## 非目标

- 本提案不实现 GPU 支持。
- 本提案暂不定义稳定的用户侧 API。
- 本提案不承诺热插拔、热迁移或超卖能力。
- 本提案不包含 mediated device、时间分片或单张物理 GPU 的多租户共享。
- 本提案不尝试为 GPU 沙箱保留当前基于快照的生命周期特性。
- 本提案第一阶段不追求覆盖所有厂商特定的 GPU 能力。

## 高层设计

本提案采用的核心模型是：将物理加速器透传给专属的 MicroVM 沙箱。

从高层看，流程如下：

1. CubeMaster 发现具备 GPU 能力的节点及其可分配加速器库存。
2. CubeMaster 将 GPU 沙箱调度到能够满足加速器请求的节点。
3. 目标节点上的 Cubelet 保留选中的设备，并准备宿主机侧运行时状态。
4. 在沙箱启动前，将选中的 PCI 设备绑定到 `vfio-pci`。
5. CubeShim 启动带有 VFIO 设备的沙箱 VM。
6. Guest image、guest kernel 和 `modules.img` 必须携带目标 GPU 栈所需的内核与用户态支持。
7. 当沙箱退出后，设备释放只能发生在 CubeShim 退出且所有设备使用者都消失之后。
8. 节点将设备恢复到后续沙箱可再次分配的状态。

这个模型刻意优先保证正确性和清晰的设备所有权，而不是一开始就追求功能覆盖面。

## 组件职责

### CubeMaster

- 定义面向加速器的调度输入和内部资源核算方式。
- 跟踪节点级 GPU 库存和分配状态。
- 拒绝无法提供独占设备所有权的调度结果。
- 保留足够的元数据，为未来扩展到 TPU 或 XPU 做准备。

### Cubelet

- 发现本地加速器设备，并上报可分配库存。
- 代表沙箱生命周期执行设备保留与释放。
- 协调宿主机侧准备工作，例如 VFIO 绑定与清理。
- 防止单节点上的重复分配。

### CubeShim

- 将 VFIO 设备挂载到沙箱 VM。
- 让设备生命周期与真实 VM 进程生命周期绑定。
- 保证正确的销毁顺序，使设备释放发生在 shim 退出之后，而不是之前。

### cube-agent

- 在启动阶段加载 guest 内所需的内核模块，例如由 `modules.img` 提供的 NVIDIA 模块。
- 配置 guest 侧 NVIDIA 运行时设置，例如 persistence mode。
- 提供 guest 侧诊断能力，用于确认透传进沙箱的加速器在 guest 内可用。

### Guest Image、Guest Kernel 和运行时栈

- 提供能够初始化并使用所挂载加速器的 guest 环境。
- 携带目标 GPU 软件栈所需的内核模块、设备文件和用户态库。

## GPU 发现、调度、分配和释放

### 发现

GPU 支持的起点是每个节点上准确的设备发现。节点本地控制面至少需要识别以下信息：

- PCI 地址
- vendor 和 device 标识
- 设备类别
- 驱动绑定状态
- 健康状态和可分配状态
- 当前是否已被其他沙箱保留

库存模型应尽量抽象为通用加速器资源，而不是只适用于 GPU，这样未来 TPU 或 XPU 也能沿用相同的控制面结构。

### 调度

CubeMaster 应将加速器请求视为硬性调度约束。请求 GPU 的沙箱只能被调度到满足以下条件的节点：

- 存在所请求的加速器类型
- 有足够数量的空闲可分配设备
- 节点具备所需的宿主机运行时栈
- 节点被标记为支持 GPU guest

第一阶段设计应假设整卡独占分配。这会比共享设备模型更容易处理调度、核算和失败恢复。

### 分配

调度完成后，目标节点必须在 VM 启动之前先保留所选设备。保留动作必须先于 VFIO 重绑定，以避免并发工作负载接入时出现竞争。

分配元数据至少应记录：

- sandbox 标识
- node 标识
- 被选中的设备地址
- 分配时间戳
- 当前生命周期状态

### 释放

设备释放不仅是控制面的状态切换。只有在以下条件全部满足后，设备才应再次被标记为可分配：

- guest 已停止使用设备
- VM 进程已经退出
- CubeShim 已退出，且不再持有 VFIO 文件描述符
- 宿主机侧清理动作已恢复到预期的绑定状态

释放路径必须偏保守。相比于过早将仍在使用的设备重新分配给第二个沙箱，宁可暂时保留一个陈旧分配记录。

## VFIO 绑定以及 shim 退出后再释放设备的关键风险

第一阶段设计中最重要的运维风险，是设备生命周期顺序。

在透传模式下，设备必须在 VM 启动前从宿主机驱动重绑定到 `vfio-pci`。但销毁阶段更微妙。如果在 guest 进程退出后立刻把设备归还给分配器，而 CubeShim 仍然持有该 VFIO 设备，那么这个释放动作就是不安全的。

设计上必须满足以下约束：

- 在 VM 启动前绑定到 `vfio-pci`
- 当 guest 仅仅开始退出时，不能立即把设备标记为空闲
- 只有在 CubeShim 退出，且宿主机确认不再有剩余持有者占用该设备后，才能释放设备

如果破坏了这个顺序，系统可能会出现“设备看似已空闲但实际仍被占用”的错误状态，进而导致重绑定失败，或者影响下一个沙箱的设备分配。这个风险应被视为第一类生命周期不变量，而不是实现细节。

## Guest Image、Guest Kernel、`modules.img` 与 NVIDIA Driver/Toolkit 要求

GPU 沙箱所需的 guest 软件栈，与纯 CPU 沙箱存在明显差异。

本提案假设 guest 侧可能需要以下全部或部分内容，具体取决于目标 GPU 软件栈：

- guest kernel 中用于 PCI 设备初始化以及所需 NVIDIA 驱动模块的支持
- 通过 root filesystem 或 `modules.img` 提供的 guest 内核模块
- guest 内部的 NVIDIA 内核驱动组件
- guest 内部的 NVIDIA 用户态驱动库
- 如果 guest 工作负载依赖该模型，则需要 NVIDIA Container Toolkit 或等价运行时集成
- guest kernel、guest modules 和 NVIDIA 驱动栈之间的版本对齐

这意味着 GPU 支持不仅是控制面问题，也会影响 guest image 的构建、版本管理、测试和分发方式。项目很可能需要显式的 GPU 能力 guest image 变体，而不能默认沿用 CPU-only 的 guest image。

## 初始设计中不支持的生命周期特性

第一阶段设计应明确排除那些与物理加速器透传天然冲突，或需要额外大量工作才能支持的生命周期特性。

GPU 沙箱暂不支持以下能力：

- 不支持 app snapshot
- 不支持从单个源沙箱进行 1:N 克隆
- 不支持 snapshot rollback
- 不支持通用 pause/resume

这些限制应作为明确的产品行为写入文档，而不是隐藏成边界情况。物理设备所有权会使这些能力比 CPU-only 沙箱复杂得多。

## 部署限制

GPU 沙箱在初始设计中依赖 PCI passthrough。

因此，基于 PVM 的部署不属于初始设计范围。

## 面向 TPU 和 XPU 加速器的可扩展性

虽然第一版提案聚焦于 NVIDIA GPU，但资源模型不应在每一层都写死为 GPU 专用假设。

设计应为以下方向预留空间：

- 将加速器类别作为通用调度维度
- 支持逐设备能力和运行时前置条件描述
- 在节点上支持不同设备类型的准备和释放钩子
- 为非 GPU 设备保留不同的透传或挂载模型

在实践中，这意味着内部资源记录、调度谓词和节点能力上报应尽可能采用“面向加速器”的抽象，而不是“仅限 NVIDIA GPU”的抽象。

## 待讨论问题

- 在不对长期 schema 过早承诺的前提下，请求加速器资源的最小用户侧 API 应该是什么？
- 加速器库存应由 Cubelet 直接上报，还是由独立的节点本地发现辅助组件上报？
- 一个节点在被标记为 GPU-ready 之前，需要通过哪些宿主机校验？
- 健康检查应如何区分可分配、故障和被管理员禁用的设备？
- NVIDIA 驱动与 CUDA 兼容性对应的 guest image 版本模型应如何设计？
- 项目是否应先只支持整卡透传，再为未来的 mediated device 模型预留扩展点？
- 如果 VFIO 重绑定成功但 VM 启动失败，失败恢复路径应该如何处理？
- 哪些加速器元数据应属于集群级调度状态，哪些应只存在于节点本地运行时状态？
- 为了支持 TPU 和 XPU，第一阶段 GPU 设计的抽象边界应如何划分，才能既不过度设计，也不把后续演进堵死？

## 总结

本提案将 GPU 沙箱定义为一种基于设备透传、强调严格设备所有权和保守生命周期处理的设计。主要复杂度不仅来自调度，还来自 CubeMaster、Cubelet、CubeShim、节点资源上报、guest image、guest kernel 模块以及 NVIDIA 运行时依赖之间的端到端协同。

设计评审通过后的下一步，应是把本提案中被认可的部分整理为分阶段实施计划。
