# Cube 驱动的内部评测执行方案

## 业务背景

某评测团队希望建设一套内测代码执行链路，用于模型评测中的脚本题目。核心诉求如下：

- 安全隔离：模型生成代码不能触碰生产环境。
- 低延迟高吞吐：每条样本都要启动一次隔离执行环境。
- 结果可复现：stdout、日志、artifact 需要保留到可追踪链路。
- 多环境一致性：不同区域、不同节点运行行为一致。

采用公有 SaaS 沙箱时，存在网络合规和启动延迟不稳定问题，最终改为自建 CubeSandbox。

## 核心痛点

- **安全边界**：执行提示词可能包含任意命令，必须限制权限。
- **并发成本**：大量短时样本导致容器模式下冷启动和资源回收有抖动。
- **产物治理**：脚本输出文件、错误堆栈、日志需要结构化留存。
- **运行漂移**：不同镜像在节点间行为不一致，影响评分稳定性。

## 基于 Cube Sandbox 的方案

团队改为“模板化 + 单次执行”模型：

1. 构建轻量评测模板，依赖精简并锁定版本。
2. 按运行场景使用不同模板（Python 基础版、Python 扩展版等）。
3. 为每条评测任务生成独立 workspace，绑定 run id。
4. 通过 `cubecli logs` 与结构化日志聚合，统一比对跨节点结果。

### 1. 模板分层

- `py-eval-basic`：基础数据处理和脚本执行。
- `py-eval-ext`：图计算/数学计算负载。
- `code-interpreter-v1`：需要较多工具链的 Agentic 场景。

### 2. 执行流

- Worker 创建带约束的 sandbox。
- 写入 prompt、输入数据和元数据。
- 将输出回传到编排器，记录 run id。
- 执行结束后销毁 sandbox；保留 artifact 供比对。

### 3. 可复现策略

- 统一超时策略（总超时 + CPU 时间限制）。
- 模板 lockfile 固定依赖。
- 统一错误码映射：超时、启动失败、运行时异常在不同语言里返回同一语义。

## 效果与收益

- 沙箱启动时间方差降低，扩容和并发稳定。
- 由于执行边界前移，安全审计更容易闭环。
- 日志与指标可对比：相同模板哈希和版本能有效复现实验偏差。
- 线上排障成本下降，模板变更可快速定位到版本边界。
