# CubeAPI Lifecycle Event Convention

> Scope: structured `LogEvent` values emitted by CubeAPI handlers, logger wrappers, and backends. This document describes the current repository implementation; HTTP Webhook and OTLP backends are not implemented.
>
> Related issue: [#642 — CubeSandbox Webhook Event Notifications](https://github.com/tencentcloud/CubeSandbox/issues/642)

## 1. Overview

CubeAPI uses structured `LogEvent` values for API telemetry and resource lifecycle results. Handlers emit events, `FilteredLogger` filters by level, `MultiLogger` fans events out, and registered backends consume them.

A lifecycle event observes an operation result. It is neither an in-sandbox hook nor part of the REST response. Emitting one does not run user code in a sandbox and must not change the API result.

**Core principles**:

- All backends reuse one `LogEvent` envelope; file, Webhook, and OTLP backends do not define separate event shapes.
- Success events are emitted only after the operation succeeds. Snapshot operations must also pass the synchronous terminal `READY` check.
- Handlers emit events but do not implement HTTP delivery, signing, or retry behavior.
- New fields must remain backward compatible. Consumers should ignore unknown fields and tolerate duplicates.
- Events must not contain secrets, credentials, complete request bodies, or other sensitive data.

## 2. `LogEvent` data format

The common structure is defined in [`CubeAPI/src/logging/mod.rs`](https://github.com/tencentcloud/CubeSandbox/blob/master/CubeAPI/src/logging/mod.rs):

| Field | JSON type | Required | Meaning |
| --- | --- | --- | --- |
| `timestamp` | RFC 3339 string | Yes | UTC time generated by `LogEvent::new`. |
| `level` | string | Yes | `debug`, `info`, `warn`, or `error`. |
| `event` | string | Yes | Stable machine-readable name; existing lifecycle events use dot-separated lowercase words. |
| Extension fields | Any JSON value | No | Context in `fields`, flattened into the top-level object by `#[serde(flatten)]`. |

```json
{
  "timestamp": "2026-07-22T08:00:00Z",
  "level": "info",
  "event": "snapshot.created",
  "sandbox_id": "sb-123",
  "snapshot_id": "snap-456",
  "names": ["checkpoint"]
}
```

`field()` stores a string and `field_value()` stores any serializable JSON value. Current code does not reject extension fields that collide with the envelope, so producers must not use `event`, `timestamp`, or `level` as extension-field names.

## 3. Mandatory rules

1. **Emit after success**: emit a lifecycle success event only after the underlying service succeeds.
2. **Snapshot terminal state**: emit snapshot create, rollback, and delete events only after `SnapshotService` confirms normalized status `READY`. Errors, missing status, and any other status must not emit a success event.
3. **Once per invocation**: emit one corresponding event for each successful handler invocation. Future backend retries may still deliver duplicates.
4. **Preserve responses**: emission must not change existing HTTP status codes, bodies, or response-header semantics.
5. **Use the source of truth**: prefer normalized IDs from successful responses; never invent unavailable context.
6. **Preserve compatibility**: adding optional fields is compatible. Removing fields, changing types, or renaming events is breaking.
7. **Separate transport**: handlers call `state.logger.log(event)` and must not send Webhooks or implement retries directly.
8. **Protect sensitive data**: do not record secrets, API keys, access tokens, credentials, Webhook URLs, or complete request bodies.

`api.request`, `api.response`, and `api.error` are handler telemetry rather than resource lifecycle success events. Only selected handlers emit them, and fields vary by handler.

## 4. Logger pipeline

```text
Handler
  -> AppState.logger.log(LogEvent)
  -> FilteredLogger (minimum-level filter)
  -> MultiLogger (concurrent fan-out)
  -> registered backends
```

| Component | Current responsibility | Implementation |
| --- | --- | --- |
| `Logger` | Defines asynchronous `log`, `flush`, and backend-name methods. | `CubeAPI/src/logging/mod.rs` |
| `FilteredLogger` | Drops events below the threshold and forwards `flush`. | `CubeAPI/src/logging/filtered.rs` |
| `MultiLogger` | Clones events and concurrently calls all backends and their `flush`. | `CubeAPI/src/logging/multi.rs` |
| `AppState` | Stores the `ArcLogger` used by handlers. | `CubeAPI/src/state.rs` |

The structured-event threshold is currently controlled only by `--debug`: it is `info` by default and `debug` with that flag. `--log-level`, `LOG_LEVEL`, and `RUST_LOG` control stdout `tracing` filtering and do not independently change the structured-event threshold.

After graceful server shutdown, CubeAPI calls `flush()` on the outer logger; wrappers forward it to inner backends.

## 5. Backend catalog

The default startup path registers only `FileLogger`.

| Backend | Status | Default | Current behavior |
| --- | --- | --- | --- |
| `FileLogger` | Implemented | Yes | Enqueues through an unbounded Tokio channel; a background task writes UTC daily rolling NDJSON files. |
| `NoopLogger` | Implemented | No | Discards events, mainly for tests or disabled logging. |
| `HttpLogger` | Stub | No | Configuration exists, but `log` and `flush` perform no HTTP delivery. |
| `OtlpLogger` | Stub | No | Does not convert events into OTLP `LogRecord` values. |

`FilteredLogger` and `MultiLogger` are wrappers, not transport backends. Commented HTTP/OTLP lines in `main.rs` are extension examples, not supported configuration.

### 5.1 File backend

```text
{log_dir}/{log_prefix}-YYYY-MM-DD.log
```

| Setting | Default | Meaning |
| --- | --- | --- |
| `log_dir` / `LOG_DIR` / `--log-dir` | `log` next to the executable; `./log` if unresolved | Output directory. |
| `log_prefix` / `LOG_PREFIX` / `--log-prefix` | `cube-api` | File-name prefix. |
| `--debug` | `false` | Whether structured `debug` events are retained. |

Each line is one complete `LogEvent` JSON object. `log()` only sends a channel message; a background task opens files, serializes, and writes. The current channel is unbounded and is not the bounded delivery queue required for a Webhook backend.

## 6. Registered event catalog

### 6.1 Generic API telemetry

| Event | Level | Current fields | Emission scope |
| --- | --- | --- | --- |
| `api.request` | `debug` | `handler` plus request context | Before service calls in health and selected sandbox handlers. |
| `api.response` | `info` | `handler` plus result context | After success in selected sandbox query handlers. |
| `api.error` | `error` | `handler`, `error` | Selected handlers that explicitly process errors. |

These events do not cover every route; consumers must not assume every call has a complete request/response/error set.

### 6.2 Sandbox lifecycle

| Event | Level | Event fields | API / emission point |
| --- | --- | --- | --- |
| `sandbox.created` | `info` | `sandbox_id`, `template_id` | After `POST /sandboxes` succeeds. |
| `sandbox.deleted` | `info` | `sandbox_id` | After `DELETE /sandboxes/{sandboxID}` succeeds. |
| `sandbox.paused` | `info` | `sandbox_id` | After `POST /sandboxes/{sandboxID}/pause` succeeds. |
| `sandbox.resumed` | `info` | `sandbox_id` | After `POST /sandboxes/{sandboxID}/resume` succeeds. |
| `sandbox.timeout.updated` | `info` | `sandbox_id`, `timeout` | After `POST /sandboxes/{sandboxID}/timeout` succeeds. |
| `sandbox.refreshed` | `info` | `sandbox_id`, `duration` | After `POST /sandboxes/{sandboxID}/refreshes` succeeds. |

These events describe operations completed by the corresponding CubeAPI handlers. Automatic transitions that bypass CubeAPI do not emit them automatically.

### 6.3 Snapshot lifecycle

| Event | Level | Required fields | Optional fields | API / emission point |
| --- | --- | --- | --- | --- |
| `snapshot.created` | `info` | `sandbox_id`, `snapshot_id`, `names` | None | Before `POST /sandboxes/{sandboxID}/snapshots` returns `201`, after create status is `READY`. |
| `sandbox.rolled_back` | `info` | `sandbox_id`, `snapshot_id`, `operation_id`, `status` | None | Before `POST /sandboxes/{sandboxID}/rollback` returns `200`, after rollback status is `READY`. |
| `snapshot.deleted` | `info` | `snapshot_id`, `operation_id`, `status` | `sandbox_id` | Before the snapshot branch of `DELETE /templates/{templateID}` returns `204`, after delete status is `READY`. |

Deletion first uses `SnapshotService::get_snapshot_context` to determine whether the ID is a snapshot. A non-empty CubeMaster `origin_sandbox_id` maps to `sandbox_id`. Legacy records without it still delete successfully and omit `sandbox_id`. Ordinary template deletion does not emit `snapshot.deleted`.

Snapshot event-name constants are centralized in `CubeAPI/src/logging/mod.rs`. Existing sandbox events still use string literals; current code has no centralized registry or subscription-validation table covering every event.

## 7. Webhook status and boundary

CubeAPI currently **does not send Webhook callbacks**. `HttpLogger` is an unregistered no-op stub. Emitting a `LogEvent` only makes it available to implemented backends such as `FileLogger`.

Current code does not provide:

- configuration for one or more endpoints or per-event subscriptions;
- JSON HTTP POST delivery;
- a bounded asynchronous queue or saturation policy;
- HMAC-SHA256 signing;
- failure retry or exponential backoff;
- a runnable receiver example or end-to-end configuration.

A future Webhook backend must reuse this `LogEvent`. Endpoint filtering, asynchronous enqueueing, signing, retry, and shutdown draining belong in the backend and require independent tests. Receivers must tolerate duplicates under at-least-once delivery semantics.

## 8. Module implementation conventions

### Handler

- Call `state.logger.log()` after service success and terminal validation.
- Use normalized response IDs and include only necessary context.
- Do not manage files, HTTP clients, signing secrets, or retry tasks directly.

### Service

- Call CubeMaster, translate errors, and validate business responses.
- Snapshot services validate `snapshot_id`, `operation_id`, and normalized `READY`; handlers do not repeat those checks.
- Represent absent legacy metadata as a missing field rather than inventing an ID.

### Logger backend

- Implement `Logger`; ensure `log()` performs no slow I/O on the request path.
- Use background tasks for network or disk I/O and test buffering, drop, and failure policies.
- Implement `flush()` so graceful shutdown can drain accepted events where possible.
- Do not leak endpoint secrets, signing keys, or sensitive fields in diagnostics.

## 9. Adding an event

1. Define a stable name and success meaning; confirm it is a lifecycle event rather than ordinary API telemetry.
2. Construct `LogEvent` at the successful terminal point and reuse `state.logger.log()`.
3. Check that extension fields do not collide with envelope fields or contain sensitive data.
4. Add a positive route test for name, level, fields, and values.
5. Add failure and non-terminal tests proving no success event is emitted and the API response is unchanged.
6. Add compatibility coverage for fields that legacy data may omit; do not invent missing values.
7. Update this catalog and its Chinese counterpart together.
8. Test filtering, signing, retry, and queue behavior in backends, not by duplicating transport in handlers.
