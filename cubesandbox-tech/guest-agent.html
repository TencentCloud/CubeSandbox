VM 里的"内应"

上一篇我们站在宿主侧看了虚拟化链路。这篇翻到墙的另一边：沙箱是一台真虚拟机，但用户要的是"容器体验"——VM 里得有人负责把宿主传来的命令翻译成真实的进程操作。这个人就是 guest agent：一个烧录进沙箱镜像、以 PID 1 身份运行的 Rust 程序。

一、问题：VM 隔离了，但里面还得跑容器

把沙箱做成 VM 有巨大的隔离收益——宿主的 CPU 漏洞、内核 bug 都无法波及 guest。但它带来一个尴尬：用户在沙箱里跑的不是虚拟机，而是容器。他们调用 sandbox.files.write()、sandbox.commands.run()，期望拿到的是"在一个 Linux 环境里操作进程"的体验。

于是需要一个"翻译层"：宿主侧传来"创建容器"，guest 里得有人真的 fork 进程、建命名空间、挂文件系统；宿主侧要读容器的 stdout，guest 里得有人把管道里的字节传出去。这个角色不能由宿主直接做——它活在 VM 里，是唯一能把"容器命令"翻译成"guest 内进程操作"的通道。这就是 guest agent。

它与宿主的通信通道是 vsock（虚拟机专用的套接字，不经网络栈），协议是 ttRPC（一种 thrift 风格的轻量 RPC）。宿主侧的 CubeShim 就是通过它指挥整个 VM 内部的。

二、机制：启动——它是 VM 的 PID 1

agent 被烧录进沙箱镜像，以 PID 1 启动。作为 init 进程，它先做系统级初始化，再把自己变成"服务进程"：

main() → real_main(): ① 日志管道（logger 任务） ② init_mode = (getpid()==1)： general_mount（基础挂载）、enable_rc_local、init_agent_as_init（挂 cgroup、设 hostname） ③ start_sandbox(logger, config, init_mode): ├─ Sandbox::new(logger) // 建立共享 UTS/IPC 命名空间等 ├─ rpc::start(sandbox, vsock://-1:1024) // 注册并启动 ttRPC 服务 └─ 信号/uevent handler → 等待 shutdown ④ shutdown 后 reboot VM

两种模式的分工很干净：PID 1 模式负责系统级初始化（挂载、cgroup、hostname）；非 init 模式（比如作为普通进程调试运行时）只启动 RPC 服务。监听地址 vsock://-1:1024 里的 cid=-1 表示"接受任意来源"，宿主的 CubeShim 随时可以连进来。

三、机制：ttRPC 服务面——它的"能力清单"

agent 对外暴露两个服务：AgentService（一切容器操作）和 HealthService。RPC 定义在 libs/protocols/protos/agent.proto。按能力分组看：

能力分组RPC
沙箱生命周期CreateSandbox / DestroySandbox
容器生命周期CreateContainer / StartContainer / RemoveContainer
进程执行ExecProcess / SignalProcess / WaitProcess
标准 IOWriteStdin / ReadStdout / ReadStderr / CloseStdin / TtyWinResize
网络UpdateInterface / UpdateRoutes / ListInterfaces / ListRoutes / AddARPNeighbors / Get-SetIPTables
运维GetOOMEvent / OnlineCPUMem / MemHotplugByProbe / SetGuestDateTime / ReseedRandomDev / CopyFile / AddSwap / GetVolumeStats / ResizeVolume

注意一个细节：这套 RPC 把"宿主发起"和"guest 执行"完全对齐——宿主说"写 stdin"，agent 就真的往容器的 stdin 管道写字节；宿主说"调整窗口尺寸"，agent 就 ioctl 终端。所有容器的 I/O 都是宿主代理转发，agent 是另一端。这也是为什么上一篇文章里暂停时要先 disconnect_agent：连接一断，I/O 转发就停了，进程还在，只是没人替它说话。

create_container 的内部处理链也值得一瞥：先 add_devices 把宿主给的设备逐个挂进 guest（virtio-blk / mmio-blk / nvdimm / scsi / vfio，带冲突检测），再把宿主 PCI 地址映射注入容器环境变量；然后 add_storages 按 Storage.driver 分派到 blk/virtiofs/ephemeral/overlayfs 各 handler；接着 update_container_namespaces、setup_bundle 准备 OCI bundle；最后 LinuxContainer::new → Process::new → start。

四、机制：就绪通知——一个"笨但可靠"的硬件握手

有个绕不开的问题：宿主怎么知道"agent 已经能接请求了"？轮询 vsock 可不可行？可行，但慢、且有竞态——你得反复尝试连接，还可能误判"还没就绪"和"已崩溃"。CubeSandbox 的选择是硬件级握手：agent 就绪后，写一个 I/O 端口，VMM 截获这个写动作，通知宿主。

// x86_64：写 I/O port 0x680，数据 0x8 let port: u16 = 0x680; let data: u8 = 0x8; libc::ioperm(port as u64, 5, 1); // 打开端口访问权限 x86_64::instructions::port::Port::new(port).write(data); // aarch64：mmap /dev/mem 0x0903_0000 写 1<<3（SYS_VSOCK_SERVER） const SYS_CTRL_MMIO_ADDR: libc::off_t = 0x0903_0000; const SYS_VSOCK_SERVER: u8 = 1 << 3;

I/O port 0x680 由 VMM 的 vsock/虚拟设备模块截获——agent 一写，宿主立刻知道"vsock server 就绪了"，随后建立 ttRPC 连接。相比轮询，硬件通知更快、无竞态、不依赖网络栈。这是那种"用一点点硬件知识换掉一大块状态机逻辑"的设计，很符合这个项目一贯的审美。

五、机制：沙箱模型——用共享命名空间实现 Pod 语义

一个沙箱里可以有多个容器（K8s Pod 语义：它们共享网络、共享进程树、共享 hostname）。agent 的 Sandbox 结构体负责建立这套共享基础：

pub struct Sandbox { shared_utsns: Namespace, // 共享 UTS（hostname） shared_ipcns: Namespace, // 共享 IPC sandbox_pidns: Option, // 可选的共享 PID 命名空间 containers: HashMap, network: Network, event_tx: Option>, // OOM 等事件广播 sender: oneshot::Sender, // 触发 VM 关机的通道 pcimap: ..., // 宿主 PCI → guest PCI 映射表 }

setup_shared_namespaces：若沙箱未指定独立 PID 命名空间，就把首个容器的 PID ns 作为共享 PID 命名空间——所有容器"看到同一个进程树"。IPC/UTS 命名空间始终共享。这就是 Pod 语义：容器们是"同一个屋子里的室友"，而不是各自独立的房间。

OOM 处理走事件广播：cgroup manager 收到 OOM 事件后，通过 event_tx（BroadcastSender）广播给所有 GetOOMEvent 订阅者——宿主 CubeShim 的 watch_oom 正是这样拿到 OOM 并转成 TaskOOM 事件上抛的。

网络也由 agent 直接管：guest 内没有 NetworkManager，agent 通过 netlink 直接配置接口与路由，写临时 resolv.conf 后 bind-mount 到 /etc/resolv.conf。这样沙箱内看到的网络与宿主 TAP 的 IP/路由严格一致，不依赖 systemd-networkd。

六、机制：rustjail——VM 内的 OCI 容器运行时

容器进程本身由 rustjail 管理——一个 Rust 版的 runc（OCI runtime）。它的启动模型是经典的 fork-exec：

LinuxContainer::new(spec) → 解析 OCI spec → init_child()：子进程入口 ├─ 读父进程环境变量（配置传递） ├─ join / create 命名空间 └─ execvp 容器 init 进程（OCI 标准启动） → start(&mut self, p): FIFO 建立、I/O 与日志 pipe、join ns、execvp、更新进程表

进程模型：每容器一个 init 进程 + 若干 exec 进程，WaitProcess 轮询退出状态。I/O 经宿主转发（ttRPC 的 WriteStdin/ReadStdout），支持 TTY（TtyWinResize 同步窗口尺寸）。这里值得点一句的是：这个"内应"要同时充当 init（系统守护）和容器运行时（进程管理），两者在一个进程里协调——它既是"管家"又是"宿主的手"，责任很重，所以协议设计上力求薄而完整。

七、机制：设备热插拔——宿主加盘，guest 自动感知

沙箱创建后可以动态加磁盘/设备。链路是：宿主 VmAddDevice → VMM 为设备分配 PCI BDF 并注入 guest → agent 的 add_device 里各 handler wait_for_pci_device（轮询 sysfs 直到设备出现）→ get_device_name_by_pci 换算 host/guest PCI 地址 → 找到设备节点 → 挂载到容器指定路径。

为什么设备热插拔重要？应用快照/模板通常只有最小系统盘，用户运行时才按需挂数据盘。能在不停机的情况下给运行中的沙箱加盘，是"模板 + 运行时扩展"模型的关键能力。另外有个安全细节：update_device_cgroup 会把 VM 根分区设备加入 cgroup deny——防止容器访问 VM rootfs，这是防逃逸的一部分。
