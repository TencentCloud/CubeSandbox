一个沙箱，是被"流水线"制造出来的

这篇讲 Cubelet 的 Workflow 引擎。创建沙箱不是一行代码，而是拉镜像、准备卷、建网络、算 cgroup、启动 VM……一长串步骤。我们把视线放到节点侧：Cubelet 是怎么把这串步骤组织成一条可扩展、可控并发、失败自愈的流水线的。

一、问题：一个"创建沙箱"的函数，会膨胀成什么

假设你是 Cubelet 的开发者，要写"创建沙箱"。你很快会发现，这不是一个函数，而是一串依赖关系明确的步骤：得先有 sandbox ID，才能建卷；卷建好，才能配网络；网络配好，才能起 cgroup；这些都好了，才能启动 VM。而每一步内部，又有多个互不依赖的子任务可以并行——比如"拉镜像"和"建网络"互不相干，让它们串行执行纯粹是浪费时间。

如果把这一切写进一个巨型函数，会怎样？函数会长到几千行，步骤顺序写死在代码里，想调整顺序要改代码，想加一种新资源类型（比如新的存储后端）要改主流程。创建时间 = 所有步骤之和，因为谁都不敢并行。

于是设计者决定：把流水线本身做成数据，让配置驱动执行。
这就是 Workflow 引擎的起点——"配置即流水线"。

解法分成两层：一层是声明式定义——流水线长什么样，写在 Cubelet/config/config.toml 里；一层是插件式执行——每个步骤是一个独立的 Action 插件，实现同一个接口。调整流水线 = 改配置；加能力 = 注册新插件。引擎本身永远不需要为具体资源类型改代码。

二、骨架：Flow / Step / Action 三层结构

流水线有三个层次：一个 Flow 是一条完整的流水线（create 或 destroy）；Flow 由若干 Step 组成（外层数组，串行）；Step 由若干 Action 组成（内层数组，并行）。真实配置长这样：

[plugins."io.cubelet.workflow.v1.workflow".flows.create] concurrent = 100 actions = [ ["createid", "appsnapshot"], # Step1：生成 ID + 快照场景准备模板（并行） ["images","volume","storage","network", "netfile","cube-sandbox-store"], # Step2：六大资源并行准备 ["cgroup"], # Step3：cgroup 资源计算与限额 ["cubebox"] # Step4：核心——创建容器并驱动 shim ] [flows.destroy] actions = [ ["cubebox"], # Step1：先销毁 VM/容器 ["images","storage","cgroup","network", "volume","netfile","cube-sandbox-store"], # Step2：并行回收资源 ["cleanup"] # Step3：GC 清理 ]

注意到 destroy 的顺序刻意反过来了：创建时最后启动的东西，销毁时最先干掉——VM 必须先死，才能安全回收它的资源。这种顺序关系，正是"依赖"在配置里的显式表达。

每个 Action 是什么，一张表说清楚：

Action职责
cubebox核心：创建容器、驱动 shim、设置宿主机 cgroup 限额（services/cubebox/local.go）
createid生成 sandbox ID（快照场景固定 templateID_0）
appsnapshot快照恢复场景：确保 runtemplate 就绪
imagesOCI 镜像拉取/确保（runtime_type io.containerd.cube.v2）
storageCubeCoW 卷/快照准备（storage_backend=cubecow）
cgroup计算资源配额（含 VM 内存开销 42MiB 等），注入 CreateContext.CgroupInfo
network调用 network-agent 建网（TAP/IPAM/策略）
volume / netfile外部卷插件挂载 / 沙箱网络文件（/run/vc/sbs）
cube-sandbox-storecontainerd SandboxStore 本地存储
cleanupGC 兜底清理（也是引擎的 cleanupFlow）

三、机制：引擎的执行规则

引擎在 plugins/workflow/engine.go，核心抽象是 Flow 接口——所有 Action 和引擎本身都实现它：

type Flow interface { ID() string Init(context.Context, *InitInfo) error Create(context.Context, *CreateContext) error Destroy(context.Context, *DestroyContext) error CleanUp(context.Context, *CleanContext) error } type Workflow struct { Name string MaxConcurrent int64 Limiter *semaphore.Limiter // 整条流水线的并发闸门 Steps []*Step } type Step struct { Name string; Actions []Flow } // Step 内 Actions 并行

执行规则有四条，每条对应一个真实问题：

① 并发闸门。进入流水线前 Limiter.TryAcquire()，拿不到信号量直接返回 ErrorCode_ConcurrentFailed。为什么？创建沙箱本身吃 CPU 和磁盘 IO，如果一台节点同时被塞进上千个创建请求，大家都会因为争抢资源而集体变慢。宁可快速失败让上层重试，也不挤兑节点——这是调度器那篇讲过的"排队限流"思想在节点侧的落地。

② Step 串行、Action 并行。逐个 Step 调用 parallelRunSteps()，内部用 errgroup.WithContext 并发执行 Step 内所有 Action——任一失败，通过 context cancel 取消其余兄弟 Action。于是创建耗时 = 串行 Step 之和，而不是 Action 之和。

③ 失败自愈。Create 失败且 Failover=true → 异步构造 DestroyContext 走销毁流水线做现场清理（防止资源泄漏——镜像拉了、卷建了、网络开了，最后 VM 没起来，不能留着这些孤儿资源）。Destroy 失败 → 调用 cleanupFlow 兜底 GC。还有一种特殊错误 PreConditionFailed 直接短路返回、不触发 failover——比如快照场景沙箱已经存在，这是预期内的，不该走销毁。

④ 插件间不直接依赖，通过上下文传数据。比如 cgroup 插件把算好的 *cgroupp.Info（CgroupID、ResourceQuantity、UsePoolV2）塞进 CreateContext.CgroupInfo，cubebox 插件在 Step4 消费它来设置宿主机 cgroup 限额。上下文还提供关键判定方法：IsCreateSnapshot()、IsRestoreSnapshot()、GetSnapshotTemplateID()——快照场景走哪条分支，由上下文说了算。

四、机制：containerd 集成——VM 也是"一个 Task"

到这里你可能会问：cubebox 插件里的"创建容器"，和普通容器有什么区别？答案是：在 containerd 眼里，一台 VM 就是一个 runtime 很特殊的 Task。这是整个设计最聪明的地方——Cubelet 以 containerd 插件身份注册（io.cubelet.internal.v1.cubebox），用进程内客户端（containerd.New(…, WithInMemoryServices(ic))）复用 containerd 的镜像、快照器与元数据，但容器的运行时指定为 io.containerd.cube.rs：

// cube_container_create.go —— createContainers 关键步骤 opts := []containerd.NewContainerOpts{ containerd.WithImageName(image), containerd.WithSandbox(sandboxID), // 挂到沙箱（非 Pod 容器） containerd.WithRuntime("io.containerd.cube.rs", nil), // 指定 cube shim 运行时 } c, _ := client.NewContainer(ctx, id, cOpts...) task, _ := c.NewTask(ctx, ioCreater, taskOpts...) // 创建 Task → containerd 拉起 CubeShim task.Start(ctx)

当 containerd 看到容器要创建 Task 时，发现 runtime type 是 io.containerd.cube.rs，就去启动 CubeShim 二进制（Shim v2）——后续的所有 Task 请求（Start/Pause/Resume/Exec）都走 shim。一个沙箱里，第一个容器（容器 0）承载 VM 本身，后续容器都是 VM 内部的 OCI 容器，由 guest agent 管理。cubebox 插件会记住 shim 暴露的 vsock 端点（cubebox.Endpoint = {Address, Version}），后面的一切 guest 通信都靠它。

runtime 路径本身也支持三级解析（withRuntimePathOpt）：OciRuntime.Path → runtemplate → annotation，优先级从高到低——这允许为不同场景注入不同的运行时模板。另外还有一个失败兜底细节：envd init 失败时走 cleanupAfterEnvdInitFailure 直接同步销毁，并把 Failover 置 false，防止二次销毁。

五、机制：暂停/恢复——三层之间的状态收敛

前面 CLM 那篇讲的自动暂停，落到节点侧就是这里：Cubelet 通过 containerd Task API 触发暂停/恢复，真正的 VM 级暂停（内存落盘）由 CubeShim 完成。难点在于——一次暂停跨越 containerd、shim、VMM 三层，任何一层半途失败，状态机都可能卡死在 pausing。

暂停（UpdateWithPause）的处理：

① 预检：IsPaused → "already paused"；IsTerminated → "not running" ② 全部容器置 PausingAt=now，doPreStop 停止任务内进程 ③ task.Pause(ctx, 30s 超时) ├─ 失败 → reconcileStatusAfterPauseError： │ 用全新 context.Background()+5s（不用已过期的 ctx）调 task.Status， │ 按 shim 真实状态收敛本地状态： │ containerd.Paused → 写 PausedAt；Running/Created → 清 PausingAt；中间态不动 └─ 成功 → 全部容器 PausedAt=now、PausingAt=0

恢复（UpdateWithResume）在非 PAUSED 状态时：RUNNING → 幂等成功；其余 → 失败。真正执行时先做资源准入检查（admitResume，受 paused_resource_release_ratio 配额约束）——暂停期间资源可能被别的沙箱占了，恢复前得确认够不够；然后 task.Resume。成功后收敛状态，并作废旧的运行时快照绑定：因为从 pausevm 目录恢复是"不透明恢复"，旧快照引用必须失效，否则下一次快照会基于错误的基底。

配套的兜底是 DeadGC：PausingAt 卡住超过 2 × taskPauseTimeout（60s），判定为卡死，走回收流程自愈。三层系统，一层一层查真实状态，是这类跨层状态机唯一的可靠收敛方式。

六、机制：状态机——用时间戳推断状态

每个沙箱对象持久化在 boltdb 里，它的状态不是显式枚举，而是由时间戳字段推断：

func (s Status) State() ContainerState { if s.Unknown { return UNKNOWN } // 优先级从高到低 if s.FinishedAt!=0 { return EXITED } // 已结束 if s.PausingAt!=0 { return PAUSING } // 暂停中（瞬时态） if s.PausedAt!=0 { return PAUSED } // 已暂停 if s.StartedAt!=0 { return RUNNING } // 运行中 if s.CreatedAt!=0 { return CREATED } // 已创建 return UNKNOWN }

为什么用时间戳推断而不是枚举？因为状态机有中间态，而中间态天然是"时间"的产物——PausingAt 一写，就进入 pausing；成功后再写 PausedAt。字段天然保存了"什么时候进入的"，DeadGC 要判断"卡了多久"，直接读时间戳即可，不用另存一份记录。这是把"状态"和"状态发生的时间"合并存储。

七、机制：快照 / 提交 / 回滚——秒级模板的根基

这三个能力支撑着"模板秒开"和"任意历史回滚"，都围绕 CubeCoW 卷操作 + shim 的 snapshot 命令。

AppSnapshot（创建模板）是离线的一次性流程：建临时沙箱 → 从 OCI spec annotations 提取 CPU/内存/磁盘参数 → 算快照路径（<snapshotDir>/cubebox/<templateID>/{cpu}C{mem}M）→ 创建内存卷 → 执行 cube-runtime 的 --app-snapshot --snapshot-type full（采集 VM 完整内存 + 文件系统）→ 写 memory.dev、rootfs → 销毁临时沙箱 → rename 到最终路径 → 登记模板元数据。

CommitSandbox 是对运行中沙箱打快照：rootfs 走 CommitTemplateRootfs；内存走 prepareCommitMemoryArtifact——如果存在可解析的快照基底，就 reflink 克隆基底做 soft-dirty 增量（只写变化的页），否则新建空卷做 full。提交后把这次 commit 标记为新的基底。

RollbackSandbox 要求新代际 > 当前 rootfs 代际。构造 rollbackRestoreConfig，通过 task.Update(WithAnnotations) 通知 shim 执行 delete_vm + resume_vm_with_config——丢弃当前 VM、从目标快照恢复，全程不写盘。期间置 RollingBack=true 防止 DeadGC 误判。

快照类型原理用途
full完整内存模板创建（一次性）
incrementalpagemap+kpageflags 只存 CoW 匿名页节省空间的完整替代
soft-dirty/proc/self/clear_refs + pagemap bit55运行时提交（默认，最小化写放大）

八、收束

问题设计关键权衡
创建流程冗长、顺序僵化config.toml 声明流水线，插件注册改流水线 = 改配置，不动代码
串行太慢Step 串行、Action 并行（errgroup）耗时 = 串行 Step 之和
创建风暴挤兑节点信号量并发闸门快速失败优于死等
失败后资源泄漏failover 走销毁流水线 / cleanup GC防孤儿资源
跨 containerd/shim/VMM 状态漂移独立超时上下文 + shim 真实状态收敛 + DeadGC以真实状态为准，不猜
一句话带走 Cubelet 把"创建/销毁沙箱"从巨型函数重构为 config.toml 驱动的插件流水线，以 containerd 插件身份复用其生态——VM 在 containerd 眼里只是一个 runtime 为 io.containerd.cube.rs 的 Task。这也是它和 Kubernetes/containerd 生态无缝集成的根本原因。
