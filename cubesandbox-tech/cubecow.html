磁盘怎么做到"一秒复制一百份"

这篇讲 CubeCoW，CubeSandbox 的存储引擎。调度器把沙箱派到了机器上，但这台机器凭什么能"秒开"一百个同模板沙箱而不爆磁盘？答案是一个叫写时复制的古老概念，加上一个"把复杂度删到几乎为零"的设计态度。我们从头走一遍。

一、问题：一百台电脑，不能有一百份系统盘

先回到那个反复出现的场景：开发者不断敲下 sandbox.create()，每次都要"开一台带 Python 3.11 环境的电脑"。如果每个沙箱都完整复制一份系统盘——几个 GB——开一百个就是一百份磁盘：空间爆炸，而且复制本身耗时。而 CubeSandbox 的核心卖点是"从模板秒开"，秒开的物理前提就是：创建沙箱不能真的复制数据。

但这一百个沙箱的系统盘内容，99.9% 是一样的——都是同一份模板。只有每个人自己的代码、下载的东西是独有的。问题于是变成：如何让一百个沙箱"共享"同一份模板的磁盘内容，各自写入时互不干扰？

二、核心思想：写时复制，用内核现成的能力

这个概念你其实早就用过——Copy-on-Write（写时复制，COW）。一间教室，老师发一本公共教材当模板，所有学生共用；谁要在书上划重点（写入），就先复印那一页，在复印件上划——其他同学仍然用原书。划重点的人越多，才会出现越多的独立拷贝。

CubeCoW 没有发明任何复杂的新东西，而是直接调用 Linux 内核已有的能力：一个叫 FICLONE 的 ioctl（ioctl 号 0x40049409）。它的语义是：

FICLONE(dst, src) = 在磁盘上登记"dst 的内容就是 src 的内容" —— 不拷贝任何字节，只加一个"引用" 只有某一方要改动某个数据块时，内核才真正复制那一小块， 让双方各自拥有。这就是 COW。

用这套语义，"创建沙箱 = 对模板文件做一次 FICLONE"，耗时与模板大小完全无关，永远是一个瞬间操作（O(1)）。这也正是 Cubelet Workflow 那篇里 storage 插件在做的：storage_backend=cubecow 时，卷的创建就是一次引用式克隆。

这里有一个技术选型值得停下来：为什么不直接用 dm-thin（设备映射薄卷）？dm-thin 同样提供 O(1) 快照，但要维护一个 pool 台账、一套内核 ioctl 编排，以及不小的崩溃恢复面。而 CubeCoW 的工作负载模式是"大量短命的、大镜像文件的克隆"——对这种模式，xfs 的 reflink（挂在 -m reflink=1 布局上）在文件层就提供同样的 O(1) 语义，且每次操作就是一个文件系统事务，崩溃语义简单得多。选择 reflink，本质是选择"更小的出故障面"。

三、三个设计取舍：把复杂度一个个删掉

真正的亮点不在"用了 FICLONE"，而在围绕它做出的三个取舍。它们让这个引擎简单到几乎不可能出 bug：

取舍一：快照"扁平化"——没有快照树

很多存储系统允许"快照的快照"，形成一棵树，树越深管理越复杂。CubeCoW 选择：无论从哪一层做快照，结果都落在最初那个卷的目录下。目录布局是：

<root_dir>/volumes/ ├── <vol-A>/ │ ├── <vol-A> ← 卷主文件（FICLONE 源） │ ├── <snap-1> ← FICLONE(<vol-A>) │ └── <snap-2> ← FICLONE(<snap-1>)，但扁平化落在 vol-A/ 下 ├── <vol-B>/<vol-B> └── ...

注意 snap-2：它是从 snap-1 克隆的，但物理上仍然躺在 vol-A/ 目录里。每个快照都记录自己的"最终源卷"，所有快照是兄弟，删除任何一个都不影响其他。代价：失去快照树的分层语义；回报：永远不用算"我的祖先是谁"，删除永远安全。

取舍二：父卷可以先删

一般理解是"子快照依赖父卷，父卷不能先删"。CubeCoW 的快照是独立的文件，不依赖祖先，允许"父卷先删、快照后删"。这正好服务一个真实流程：构建模板时先建临时卷，完成后删临时卷——快照安然无恙。对运维来说少了一个"先删谁后删谁"的纪律约束，就少了一类操作失误。

取舍三：崩溃恢复靠"扫描目录"，而不是日志

传统存储系统要写事务日志（WAL）才能保证崩溃后一致。CubeCoW 的选择更简单：目录结构本身就是状态。启动时扫一遍磁盘，就能重建全部元数据——卷列表来自 readdir(volumes/)，快照列表来自 readdir(volumes/<vol>/) 减掉主文件，大小来自 stat，创建时间来自 mtime。扫描器还负责清理上次崩溃留下的孤儿：空目录、FICLONE 没落地的零字节快照文件。代价：要求每步操作严格先落盘再返回；回报：没有日志、没有 WAL，代码少一大截。

四、为什么这套设计"敢"这么简单

这三个取舍成立的前提，是 CubeCoW 刻意押注在一个假设上：底层文件系统（xfs）已经把它最难的部分做好了。引用计数、空间回收、掉电一致性——全是内核的事。CubeCoW 只做三件事：起名字（校验名称合法性）、建目录、调 FICLONE。它甚至启动时还会探测一次底层文件系统是否真的支持 FICLONE，不支持直接拒绝启动，而不是运行到一半才炸。

也正因为"卷 = 一个普通文件"，它才能用最薄的接口暴露能力：对外是一个 Engine trait（create/delete/resize/list volume、snapshot 操作、激活/停用），再通过 C FFI 层（ffi.rs + cubecow.h）暴露给 Go 侧。CubeSandbox 的节点管理程序（Go 写的 Cubelet）通过 cgo 调用它——两边语言不同，但接口薄得一眼看穿。

一个反直觉的结论：越基础的基础设施，越该把"简单可靠"放在"功能强大"前面。
存储引擎是沙箱数据安全的最后防线。每删掉一个复杂机制（快照树、事务日志、pool 台账），就少一类能出故障的状态。CubeCoW 的"设计审美"，是把能不做的事全都不做。

五、收束

问题选择付出的代价
克隆模板太贵FICLONE 引用式克隆，O(1)依赖底层文件系统支持 reflink
快照树难管理扁平化，全部落在源卷目录失去分层语义
父卷先删会悬空快照独立，父卷可先删无（少一条操作纪律）
崩溃后不一致目录即状态，扫描自愈每步必须严格先落盘
一句话带走 CubeCoW = 用内核自带的 FICLONE 把"克隆模板"变成 O(1) 的瞬间操作；再配合三个删繁就简的取舍（无快照树、父卷可先删、扫描自愈），换来一个简单到几乎不会出错的存储层——而"秒开一百个沙箱"的物理基础，就在这里。
