一台闲置的沙箱，怎么自己学会"睡觉"

这篇讲 cube-lifecycle-manager（CLM）。我们从成本问题出发：沙箱不用的时候也在烧钱，但用户随时可能回来。CLM 的答案是把闲置沙箱"暂停"成快照、需要时再"唤醒"——而"判断何时该睡、何时该醒、醒来谁来做"，是一个分布式系统里最考验并发设计的问题之一。

一、问题：闲置的沙箱，是纯成本

沙箱的计费对象是"存在时间"，不管用户用不用。而现实里，开发者开一个沙箱，真正的使用往往只有几分钟，剩下的几个小时它都闲着——一台 VM 占着内存、占着 CPU 配额，什么也不干。

前一篇调度器里我们见过"模板秒开"：沙箱本质是"模板快照 + 内存快照"，既然创建时能从快照恢复，那暂停时把内存写回快照、恢复时再拉起来，就是一条自然的路径。于是设计目标明确了：

需求含义
自动暂停沙箱空闲超过阈值，自动把 VM 内存落盘、释放资源，只剩一份快照
自动恢复用户请求到达暂停的沙箱时，从快照毫秒级唤醒，体验上"只是首请求稍慢"
收敛一致手动 pause/resume（SDK 调用）与自动逻辑并存，最终状态必须一致

问题被翻译成一个工程任务：谁来判断空闲、谁执行暂停、谁响应唤醒、如何防止多副本重复操作。这就是 CLM 存在的理由。

二、为什么需要一个独立组件

一个自然的想法是：把扫描闲置的逻辑塞进 CubeMaster 里不就行了？但这样有两个问题。第一，CubeMaster 的主链路是请求驱动的调度，它必须保持"无状态、专注于转发"——扫描、定时、状态维护是另一种节奏，混在一起会让主链路的故障面变大。第二，"自动化策略"（多久算闲置、是否自动暂停）需要独立升级、独立扩缩容，绑在主服务里就没法单独动了。

所以 CLM 被做成一个独立的 sidecar 部署在控制面，它自己不执行暂停/恢复，而是"协调"：从 Redis 事件流里看发生了什么，向 CubeMaster 发 RPC 让它暂停/恢复，把状态推给 CubeProxy 让数据面知道"这个沙箱现在能不能接请求"。启动时，main.go 装配了五个内部循环，各管一摊：

循环职责
consumeStreamXREADGROUP 消费生命周期事件（block 5s、count 100、出错退避 1s）
pollLastActive周期轮询所有 CubeProxy 的 /admin/last_active，合并活跃时间戳
sweep.Run空闲超时扫描，默认每 5s 一次
apiSrv.RunHTTP 面：/internal/resume、/healthz、/readyz
discSvc.RunCubeProxy 副本发现（Redis 心跳注册表）

三、机制之一：Redis 事件流，唯一的"事实源"

CLM 判断"世界上有哪些沙箱、处于什么状态"，依据不是自己去问，而是订阅一条事件流。CubeMaster 在每次创建/销毁/更新成功后，把元数据和事件写进 Redis；CLM 消费后，在内存里建起自己的注册表（registry）。

Redis Key结构说明
…sandbox:lifecycle:metaHashfield=sandbox_id，value=生命周期元数据 JSON，供启动时全量引导
…sandbox:lifecycle:eventsStreamXADD 事件（MAXLEN ~100000），字段 op / sandbox_id / payload / ts
…sandbox:lifecycle:state:<id>String当前状态（paused/running/pausing…），兼作 SETNX 状态锁（第四节）

事件有四种 op：create / delete / update / state。其中 state 事件带 StatePayload{state, actor, source}——state 只允许 paused/running，actor 区分是谁改的（cubemaster 还是 clm），这为后面的"状态对账"埋下伏笔。

消费侧有几个工程细节。启动引导（bootstrap）时用 HGetAll 全量加载 meta，并且强制以 hash 的 field 作为 sandbox_id——防御脏数据，不能信 value 里可能写错的 id。消费者组用 XGroupCreateMkStream 创建，多副本 CLM 共享同一个消费组，事件不会重复处理；遇到 BUSYGROUP 错误就忽略（说明别的副本建过了）。遇到解析不了的事件，先 Ack 再丢弃——不处理，但也不能让它卡住整条流。

四、机制之二：扫描决策——"它到底闲没闲"

注册表建好了，每 5 秒 sweep.Run 扫一遍，找出"空闲超时"的沙箱。问题来了：怎么判定一个沙箱闲了多久？

活跃时间的定义是：跨所有 CubeProxy 副本取 LastActiveMs 的最大值，再和元数据里的创建时间取 max。为什么跨副本取 max？因为用户可能从任何一台 CubeProxy 进入，单看一台会低估活跃度。公式如下：

baseline = max( 各 CubeProxy 上报的 LastActiveMs, Meta.CreatedAt ) （若两者皆 0，回落 FirstSeenAt —— CLM 本地首次见到它的时间） timeout = Meta.TimeoutSeconds （nil → 集群默认；< 0 → 永不暂停） idleFor = nowMs − baseline idleFor < timeout → 跳过（还没到点）

这个"空闲判定"里有三个陷阱，代码里各有对策：

陷阱一：CLM 重启会误杀。重启后从 HGETALL 引导进来的老沙箱，LastActiveMs 还是 0——如果立即扫描，会误判"从未活跃、立刻超时"。对策是 BootstrapWarmup：启动后 30 秒内，跳过那些"首次见到时间 ≤ 启动时间"的条目，等 pollLastActive 把真实活跃时间回填。

陷阱二：状态锁可能过期。扫描前先 GetState，若已经是 paused/pausing/killing/killed，直接跳过——避免对一个正在处理中的沙箱做无谓 RPC。

陷阱三：多副本同时扫到同一个沙箱。这是分布式系统最经典的竞态，解法是"状态即锁"：

tryPause(sid)： ① AcquireState(sid, "pausing", TTL=60s) // SETNX：抢到锁才继续，抢不到 = 别人在处理，直接返回 ② ProxyPush.SetState(sid, "pausing") // 先通知 CubeProxy 门禁（失败仅告警） ③ CubeMaster.Pause(sid) // POST /cube/sandbox/update {action:"pause"} ├─ 404(沙箱不存在) → 驱逐本地条目：清状态 + 删 meta + 删注册表，视为成功 ├─ 已处于目标态 → 落入"成功记账"（补写 paused） └─ 其它错误 → 回滚：清状态锁 + 写回 running + 返回错误 ④ 成功记账：SetState(sid, "paused") + ProxyPush.SetState(sid, "paused")

销毁（tryKill）结构相同：抢 killing 锁 → 通知代理 → DELETE 沙箱（kill_reason=timeout）→ 成功后清理。这套 "状态即锁"的设计把"状态表示"和"并发控制"合二为一——state key 既是 CubeProxy 查询的门禁依据，也是 CLM 操作的互斥锁，TTL 兜底防止执行者崩溃后锁被永久占用。一个 key，两用，代价是必须在语义上小心设计。

五、机制之三：自动恢复——十个并发请求，只唤醒一次

暂停是 CLM 主动发起的，恢复则是请求驱动的：CubeProxy 数据面遇到一个 paused 沙箱的请求，回调 POST /internal/resume。这带来一个高并发问题：同一沙箱同时来了 10 个请求，恢复只能做一次，另外 9 个得等同一个结果。

解法是"单飞合并"（singleflight 模式）：CLM 内部维护一个 calls[sid] 表，第一个请求创建 in-flight call，后续请求发现已有 in-flight，直接 select 等它的 done 通道，共享第一个执行者的结果。恢复执行本身还要再过一道状态锁：

Resume(sid)： 锁内查 calls[sid] ├─ 已有 in-flight → 等 done / ctx.Done() → 返回首个执行者的结果 └─ 无 → 新建 call，执行 doResume： acquireResumeOwnership：SETNX "resuming" 锁 ├─ cur == "running" → 幂等成功（already running） ├─ cur == "pausing/resuming" → waitForRunning 等对端结果 └─ cur == "paused" / 不存在 → 抢锁成功，own 路径 AutoResume 门：!Meta.AutoResume → 放弃（必须显式 connect()） callCubeMasterResume：POST /cube/sandbox/update {action:"resume"} └─ 404 → 驱逐注册表；已处于目标态 → 视为成功 成功记账： SetState("running") go pushRunningState(sid) // 独立 3s 超时 + 指数退避（100ms→200ms，3 次） Registry.MergeLastActive(sid, now) // 刷新活跃时间，防 sweeper 立刻再暂停

有两个细节值得注意。一是 waitForRunning 的轮询：以 200ms 间隔轮询状态直到 running，如果状态锁在轮询中途过期（TTL 60s），返回错误而不是假装成功——宁可失败重来，不给用户一个虚假的成功。

二是 MergeLastActive。每次自动恢复成功后，把活跃时间刷新到当前——沙箱获得一个全新的计时窗口。于是"恢复 → 使用 → 再次空闲 → 再次暂停"的循环可以无限持续。这是 Agent 场景成本优化的核心：闲置就睡，来请求就醒，睡和醒之间用户无感。

六、机制之四：状态对账——手动与自动，收敛到同一事实

除了 CLM 的自动暂停/恢复，用户也可能通过 SDK 直接调用 pause()/resume()（走 CubeMaster）。这两条路径并存，必须保证最终一致。CubeMaster 的操作成功后同样会发 state 事件，CLM 消费后走对账：

Handle(ev)： ① 校验：op=state、state ∈ {paused, running}、注册表里有该沙箱 ② 若当前状态是 "pausing"/"resuming" → 跳过（CLM 自己的 in-flight 流程会写终态，避免竞争） ③ 幂等：当前状态 == 新状态 → 直接返回 ④ 对账：SetState(newState) + ProxyPush.SetState(newState) newState == "running" → 额外 MergeLastActive（防止刚恢复又被扫暂停）

这套设计的价值在于：事件驱动 + 幂等对账，让"谁发起的操作"在最终状态上收敛一致，不依赖事件到达的时序。即使事件乱序，最终也会幂等收敛到真实状态——这就是"最终一致性"在一个具体系统里的落地。

七、收束：设计全景

问题机制核心权衡
谁来判断沙箱闲了多久事件流 + 跨副本 max 活跃时间事实源唯一，判定可审计
多副本同时扫描到同一沙箱"状态即锁"（SETNX + TTL）状态表示与并发控制合一
并发请求同时唤醒一个沙箱singleflight 合并 + 状态锁一次恢复，N 个等待者共享结果
重启误杀闲置沙箱BootstrapWarmup 30s 宽限正确性优先于即时性
手动与自动操作并存事件驱动 + 幂等对账不依赖时序，最终收敛
一句话带走 CLM 是一个事件驱动的"寿命管家"：Redis 流是事实源，sweeper 用 SETNX 状态锁做幂等的暂停决策，resumer 用单飞合并做请求驱动的唤醒，statesync 让手动与自动收敛一致——闲置就睡，来请求就醒，全程用户无感。
