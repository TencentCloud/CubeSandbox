请求怎么找到沙箱，又怎么叫醒它

这是九篇的收官。CubeProxy 是系统的入向大门：外部请求带着一个沙箱 ID 进来，它要路由到那台机器上的那个端口。而它还有一个更妙的职责——如果目标沙箱正在"睡觉"（被 CLM 暂停了），它不是返回错误，而是把沙箱叫醒再继续转发。我们看这条链路怎么设计。

一、问题：入向路由的两道难题

外部请求要到达沙箱，得先回答两个问题。第一，路由：请求里带着沙箱 ID 和端口，怎么翻译成"哪台宿主机的哪个端口"？宿主机、沙箱的 IP 是动态分配的，路由表必须实时、可查。第二，状态：沙箱可能被自动暂停了（CLM 的功劳），此时请求打到它身上会发生什么？返回"沙箱不存在"当然简单，但用户会觉得"我的沙箱怎么丢了"——体验上应该是"等一小会儿，它醒了"。

CubeProxy 的设计里，两个难题的解法是耦合的：它解析后端时顺便拿到沙箱的生命周期状态，然后路由前先过一道"状态门禁"——该叫醒就叫醒。我们顺着一个请求的路径走。

二、入口：双模式解析

CubeProxy 同时支持两种 URL 约定，方便不同场景的客户端。E2B SDK 走经典的 Host 模式：

Host 模式（rewrite_phase.lua）： Host: 80-a1b2c3d4e5f6.domain.com │ └──────────┬───────────┘ │ └── 正则 ^(%d+)%-([^%.]+) 提取 │ port="80", sandbox_id="a1b2c3d4e5f6" ▼ resolve_backend(sandbox_id, port) → route 到沙箱 IP:port，重写 Host 头

通用场景走 Path 模式：

Path 模式（path_rewrite_phase.lua）： URI: /sandbox/a1b2c3d4e5f6/80/rest/of/path ├─ sandbox_id = "a1b2c3d4e5f6" ├─ port = "80" └─ rest = "/rest/of/path" → 重写为实际容器路径 同时设置 proxy_redirect / proxy_cookie_path：让容器里的重定向/Cookie 也带 /sandbox/<id>/<port> 前缀；X-Forwarded-Prefix：/sandbox/<id>/<port>

为什么维护两套？Host 模式对 SDK 用户最透明（URL 结构不用改），但依赖 DNS 泛解析；Path 模式适合"一个域名服务多个沙箱"或没法配置泛解析的环境。两种模式最终都汇入同一个 resolve_backend——解析逻辑只有一份，避免了双份维护。

三、机制：后端解析——两级缓存

解析后端是"先本地、后远端"的两级：

resolve_backend(sandbox_id, port)： ① 查共享字典 sandbox_backend_cache（key = sandbox_id:port） ├─ 命中且未过期 → 返回 backend{ip, host_port, meta} └─ 未命中/过期 → 查 Redis ② Redis：按 sandbox_id 取 meta（HSET 结构，含 host_id/host_ip/端口映射） → 组装 backend → 写回本地缓存 ③ 仍然失败 → 判定沙箱不存在 → 返回 nil（触发 404 / 门禁逻辑）

这个两级设计的动机是延迟：共享字典在进程内，查询是微秒级；Redis 在远端，每次查询都有网络往返。把热点数据缓存在本地，是典型的"以内存换延迟"。而解析结果里顺带携带的生命周期状态和 last_active 水位，正是下一步门禁逻辑的输入——所以解析不能只返回"地址"，必须返回"地址 + 状态"。跨多个 CubeProxy 副本时，last_active 取各副本上报的最大值（由 CLM 轮询汇总）。

四、机制：状态门禁——自动恢复的最后一公里

请求解析到后端后，不是直接转发，而是先过状态门禁（sandbox_state.gate）。这是整个"自动暂停/自动恢复"闭环里最精妙的一环：

sandbox_state.gate(backend)： 根据 backend 的状态字典（state:<id>）分支： ├─ running → 放行 ├─ paused → 触发自动恢复： │ ngx.location.capture("/_sidecar_resume", {args={sandbox_id=…}}) │ → 内部子请求调用 CLM: POST /internal/resume（阻塞等待恢复完成） │ → 恢复成功 → 重试路由；失败 → 503 ├─ pausing → 503 + Retry-After（马上就好） ├─ killing / killed → 410 Gone（沙箱即将/已被销毁） └─ 未知 → 404

关键设计是"阻塞式恢复"：请求到达一个 paused 沙箱时，数据面不返回错误，而是阻塞几百毫秒到一两秒，等 VM 从快照恢复，然后重试路由。对用户来说，这是"首次请求稍微慢了一点"，而不是"一次失败"。配合 CLM resumer 的并发合并（那篇里讲过），同一沙箱的并发请求只触发一次恢复，其余等待同一个结果。

这就是为什么整个系统敢做自动暂停：暂停省的是机器的资源，用户无感是因为 CubeProxy 在门口替你等着叫醒。省资源与好体验之间的鸿沟，由这个门禁补上。

五、机制：动态选路——没有静态 upstream

转发本身也做了一个不常见的取舍：CubeProxy 不配置静态 upstream 块，而是在 balancer 阶段动态指定每个请求的目标：

balancer_phase.lua（balancer_by_lua_block）： 从当前请求上下文取 resolve_backend 的结果 → balancer.set_current_peer(backend.ip, backend.host_port) 没有静态上游服务器，peer 完全由 Lua 每请求决定 → 沙箱 IP 由元数据驱动，宿主机迁移/重建后自动生效，无需 reload

为什么值得这样？如果写死 upstream 列表，沙箱 IP 一变（宿主机重建、沙箱迁移）就得 reload nginx。动态选路让 peer 完全由 Redis 里的元数据驱动——元数据变了，下一跳自然就对了，配置零维护。配合 maskRequestHost（request_host.lua 按 ${PORT} 模板渲染重建上游 Host 头），保证沙箱内应用看到的 Host 与其被调用端口一致——多端口服务场景下这是必需的，否则容器里拿到的主机名对不上。

六、机制：注册与心跳——让自己被发现

CLM 需要知道"有哪些 CubeProxy 副本"来轮询 last_active 与推送状态——靠 Redis 注册表自我宣告：

init_worker_phase.lua（每 worker 启动）： HSET cube:v1:shared:cube_proxy:registry <proxy_id> {admin_url, resume_url, node_ip, started_at, version} ZADD cube:v1:shared:cube_proxy:heartbeat <unix_ms> <proxy_id> （心跳 TTL 15s，按 3s 周期刷新；过期成员由 CLM 的 discovery 清理） 同时： 从 Redis 拉取沙箱 meta 建立本地缓存基线 admin_phase 提供： POST /admin/meta/upsert ← CLM 推送沙箱元数据 POST /admin/meta/delete ← CLM 通知沙箱销毁 POST /admin/state ← CLM 推送状态变化 GET /admin/last_active?since=… ← CLM 轮询活跃水位（X-Cube-Admin-Token 鉴权）

三管齐下保证"任何时刻每个副本都有全量路由信息"：新副本靠 bootstrap 拉全量，存量副本靠 admin 事件推送增量，故障副本靠心跳过期被剔除。一个分布式系统里最经典的三个数据同步模式，在这里各司其职、互相兜底。心跳用 ZADD + TTL 15s + 3s 周期：副本活着就持续刷新自己的分数（时间戳），死了就自然过期，CLM 扫到就清理。

七、收束

问题设计关键权衡
两种客户端 URL 约定Host 模式 + Path 模式，汇入同一解析兼容 E2B SDK 与通用场景
路由表要实时shared dict + Redis 两级缓存内存换延迟
请求打到已暂停沙箱状态门禁阻塞式唤醒用户无感，代价是首请求延迟
沙箱 IP 会变balancer 动态选路，无静态 upstream零 reload，元数据驱动
多副本信息同步bootstrap 拉全量 + 事件推增量 + 心跳剔除三种模式各司其职
一句话带走 CubeProxy 是双模式请求路由 + 两级后端解析 + 状态门禁驱动的自动唤醒 + balancer 动态选路 + Redis 注册表自我宣告的无状态数据面——它是 E2B 兼容的入口，也是"自动暂停"在用户请求侧的无感保障。
