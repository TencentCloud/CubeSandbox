一台沙箱，该落在哪台机器上？

这篇讲 CubeMaster 的调度器。我们从问题出发，一层一层看它如何被逼出现在的样子：先解决"选得动"，再解决"选得对"，然后解决"扛得住"。每层的机制、以及机制背后的权衡，都会讲到代码层面。读完你应该能闭着眼画出完整的选位流水线。

一、问题：选一台机器，难在哪

你敲下 sandbox.create()，说"我要一台 4 核 8G 的沙箱"。后台有一百台物理机，每台上百个沙箱。系统的任务是：从这一百台里挑出一台，来承载你的沙箱。

这个选择，要在三个维度上同时成立，缺一个就会出事：

维度具体问题违反的后果
资源（选得动）机器剩下的 CPU/内存/磁盘，装得下这个请求创建失败，用户重试，体验崩坏
均衡（选得对）负载不能一边倒，也不能在几台机器间震荡有的机器挤爆，有的空转，资源浪费
时效（选得快）整个决策必须压缩在几十毫秒内完成创建响应变慢，秒开变慢开

调度器入口是 Select()（CubeMaster/pkg/scheduler/schedule.go）。它不真正创建沙箱——创建发生在节点上的 Cubelet 进程里——它只负责"选位"。但选位的每一步，都和上面三个维度较劲。我们把调度器当作一条四段流水线来看，后面的内容都是围绕它展开的：

带模板 ID 的请求：淘汰失败 → 直接报错返回，不走兜底（shouldSkipBackoffForTemplate）

二、第一层设计：淘汰——"装不下"的直接回答

最天真的做法是随机挑一台，但这会把请求砸到快满的机器上，创建失败。第一层进化由此而来：先把装不下的机器淘汰掉，剩下的才叫候选。淘汰在代码里叫 Filter，每一关是一个独立的函数，实现同一个接口 Select(selCtx) (node.NodeList, error)。五关判据如下：

关卡判据（淘汰条件）出处
cpuFilter有效空闲 CPU ≤ 请求，或节点 CPU 利用率 ≥ 80%filter/cpufilter.go
memFilter有效空闲内存 ≤ 请求；或实时负载内存不够「请求 + 预留」filter/memfilter.go
diskFilter存储盘 / 系统盘 / 数据盘任一分区使用率 ≥ 80%filter/diskfilter.go
realtimecreatelimit正在创建数 ≥ 节点上报的创建并发上限（默认 50）filter/realtimecreatelimit.go
template_locality模板快照不在本机（第五节详述）filter/template_locality.go

“有效空闲”背后的两个算法决定

CPU 和内存两关的核心是同一个公式：

有效空闲 = 上报配额 × 超售比(overcommit ratio) − 已分配量 （源码：EffectiveQuotaCpu / EffectiveQuotaMem − EffectiveAllocated，config.go）

这里有两个算法决定，值得停下来理解。

第一是超售。沙箱实际用不满上报的配额——4 核的沙箱，多数时间 CPU 只用到几十个百分点。如果按上报值严格相加，一台 64 核的机器放 16 个 4 核沙箱就"满了"，剩下 80% 容量空转。超售比就是对"配额"和"实际占用"之间差距的承认：有效配额 = 上报配额 × 超售比。代价是风险——万一所有沙箱同时打满，物理机真的会超载，所以这个比值不能拍脑袋定，是整个集群运营中最敏感的调参点之一。

第二是"已分配量"从哪来。它等于这台机器上所有沙箱承诺出去的配额之和，记录在 Redis 里，由各节点上报。这里有一个例外开关：如果 Redis 的分配记录不可信（比如节点闪断漏报），可以配置 ignore_redis_allocation，让调度器把已分配当作 0 来算——宁可冒险多放一点，也不让脏数据卡死整个集群。

内存关比 CPU 关多一道检查：实时负载防线。配额是承诺，实际占用是另一回事——节点上报的实时内存 MemMBTotal − MemUsage，必须能盖住「你的请求 + 预留」。预留默认 10GB，给机器留呼吸空间；小机器则按配额比例的 10% 兜底。这道防线防止的是：配额账面上有富余，但实际内存已经吃紧。

另外，五关是并行执行的，实现是 Go 的 errgroup + 计数器（parallelRunFilters()，schedule.go）：每个节点被某一关放行一次就记一票，最后只保留票数等于关卡总数的节点。一票否决，全票才留。

三、第二层设计：打分——"装了之后会怎样"的效用评估

淘汰只回答"能不能装"，但它制造了一个新问题：大家会往同一两台"最好"的机器上挤。如果这些机器装得下，所有人都选它们，直到被淘汰关拦下才流向下一台——集群负载永远一边倒。

第二层进化由此而来：给通过淘汰的机器打分。分代表"这台机器接下你这单之后的综合处境"，越高越好。打分在 runScoreFilter() 完成，四路插件各有权重、各有关闭开关，不想要的路可以直接禁用。四路分是：

插件计算什么作用
affinityscore用户偏好的机器（k8s 亲和语义换算分）尊重用户显式意愿
imagescore镜像/模板在本机缓存的命中情况让秒开成为可能
realtimeweighted实时负载因子 + 剩余资源越多分越高负载均衡的数学化
multifactorscore后台预计算的综合分，直接读取把耗时算在选位之前

三个机制层面的细节，把它们讲透：

① 打分本质是"效用函数"。realtimeweighted 的负载均衡项写成公式就是：

剩余资源分 = getReciprocal(有效配额 − 已分配 − 你的请求, 有效配额) —— 机器在承接你这单后剩得越多，这一项分越高

它让"空机器"天然得高分，流量就会被"没用完的地方"吸引过去，集群负载趋于均匀。注意这里减去了"你的请求"——打分评估的是承接后的处境，而不是当前处境。

② imagescore 的映射曲线是有讲究的。模板快照的大小从 23MB 线性映射到 80GB×容器数：快照越小、克隆越省事，分越高。低于 23MB 一律按 23MB 算（不给零分），超过上限封顶为满分。这条曲线把"模板本地性"这个产品特性，量化成了调度依据。

③ 综合分是预计算的，这是"几十毫秒选位"的关键。multifactorscore 背后有个后台协程 loopAsyncScore()：每 50ms 醒一次、按配置间隔节流，把全集群所有健康节点的综合分提前算好存进缓存。真正选位时直接读 n.Score，不再现场遍历一百台机器。用提前算好的代价，换选位瞬间的极致延迟——这是调度系统里非常典型的时间换空间。

最后，各路的原始分乘上自己的权重求和，再除以总权重归一化（跳过关掉的路），每台机器得到一个 0–1 之间的分，按降序排好。

四、第三层设计：抽签——以及"永远选最好"为什么是错的

分数排好名次，最后一步是选。这里有一个反直觉的设定：默认情况下，调度器不是选分数最高的一台，而是从高分集合里随机挑。

选择逻辑是 LeastRandomSelect()（selctx/selectcontext.go）：

① 取按分数排序后的前 N 名（PrioritySelectNum，默认 -1 = 全部保留） ② 把每台机器的分放大为权重：int(Score × 1e6) ③ 用权重构造选择器，随机抽出一个 选择器算法由 least_select_name 配置： random → 均匀随机（默认，忽略权重） sw/rrw → 平滑加权随机（分数越高，中选概率越大）

默认用均匀随机，是有意为之。回忆一个场景：如果"永远选最高分"，会发生什么？所有流量扑向第一名，把它打满；打满后它分数暴跌，流量再涌向新的第一名……集群在几台机器间来回震荡，永远安分不下来。而均匀随机保证流量天然散开——代价是偶尔选到次优，换来长期的均衡。

这也是集群调度领域的通识：不追求单次最优，追求整体稳定。分数排序的真正用途，是给可选的加权算法提供权重依据；而默认行为刻意保守。

五、兜底路径，和模板那道"不兜底"的铁律

淘汰层有个兜底设计：万一五关把候选清空了，普通请求不会直接失败。调度器会走 BackoffSelect()：用一套更宽松的条件（跳过部分淘汰，按健康度从集群里捞一批），再 rand.Intn 随机挑一台顶上。宁可放宽标准，不让请求白跑一趟。

但这个兜底，在模板面前失效了。回到模板本地性：CubeSandbox 的招牌是"从模板秒开"——模板是一份打包好的 rootfs + 内存快照，新沙箱克隆一份、恢复快照，几十毫秒起。这一切的前提是：模板快照就在你选中的那台机器上。模板在 A 机、沙箱被派到 B 机？B 得先跨网络搬模板，你的 60ms 变成 6s。

所以模板本地性被做成一道淘汰关 template_locality，它按三层校验：

校验逻辑
① 显式限定请求可指定 TemplateNodeScope（模板只能落在哪些节点），不在范围的淘汰
② 镜像缓存GetImageStateByNode(templateID, nodeID) 查不到这份模板快照 → 淘汰
③ 快照可写请求带 EnforceSnapshotStorage 时，要求快照存储存在且可写

而它的特殊之处在于兜底豁免：schedule.go 里 shouldSkipBackoffForTemplate() 规定——只要请求带模板 ID 且注册了这道关，淘汰失败就直接返回 SelectNodesNoRes，绝不进入 BackoffSelect。逻辑是：模板都不在那台机器上，兜底挑中了也是一场注定慢 6 秒的启动。与其制造一个"能开但慢得离谱"的沙箱，不如明确告诉上层"没有合适的地方"，让上层决定报错或重试。

六、最后的防线：洪峰限流，源头就把水龙头拧小

前面都是"选谁"的问题。还有一个更粗鲁的：活动日一千人同时创建，请求洪水一样涌进来。如果全部立刻分派，每台机器要同时启动几百个虚拟机——启动虚拟机本身极吃 CPU 和磁盘 IO，瞬间所有创建通道堵死，已运行的沙箱跟着卡顿。这是"自己把自己挤兑死"。

解法分两层，都在 pkg/scheduler/local.go 和 pkg/base/bufferqueue/：

第一层：排队桶。按机器配置（instance_type）分桶，每桶一个队列，请求先入队，工人按并发上限一个一个处理。队列的数据结构是两个部件的组合：一个按入队时间戳排序的小顶堆（TimeSortedQueue，priority 取 time.Now().UnixNano()，天然先进先出），一个信号量（semaphore.Weighted）卡住并发。工人拿不到名额就睡 1ms 重试。为什么分桶？4 核和 32 核机器能承受的并发不同，混在一队，小机器会被大请求堵死。

第二层：水位自动升降。并发上限不是写死的。monitorLimit() 每 5 秒重算一次：

每节点创建上限 = max( 集群总创建并发 ÷ 健康节点数, 100 ) 全局创建并发 = ceil( 健康节点数 × 每节点上限 ÷ Master 副本数 ) 销毁并发同理，按每节点 50 计算

算出的水位和当前不同，就用 SetLimit() 动态改信号量。集群扩容了水位自动抬高，节点挂了自动收紧，全程无人值守。如果水位写死，活动日扩容了机器够用却仍按旧上限拒客，那才叫事故。

七、收束：这条设计之路的全貌

回头看，每一层设计都是被一个问题逼出来的，环环相扣：

问题逼出的设计关键权衡
随机挑会挑到快满的机器五关并行淘汰，全票通过超售换容量，预留防过载
淘汰后大家挤向"最好"的机器四路效用分，加权归一化预计算换选位延迟
"永远选最高分"导致热震荡默认均匀随机，加权可选稳定优先于最优
模板不在本机，秒开变慢开模板本地性淘汰 + 失败不兜底宁可拒绝，不制造慢启动
创建洪峰挤兑后端分桶排队 + 水位自动升降快速失败优于死等
一句话带走 调度器是一条四段流水线：预选 → 五关淘汰 → 四路打分 → 抽签。它的每个部件都对应一个真实问题，而贯穿始终的设计哲学只有一句——不追求单次最优，追求整体稳定。
