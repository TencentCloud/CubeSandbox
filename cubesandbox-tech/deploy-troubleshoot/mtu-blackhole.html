CUBESANDBOX · 部署排障 03 / 05

HTTP 通、HTTPS 超时、大文件截断——一次 MTU 黑洞的完整修复

DNS 修好后，沙箱能解析域名了。可诡异的事情来了：`curl http://www.baidu.com` 返回 200，`curl https://www.baidu.com` 却超时；1MB 的下载文件只收到 228KB 就断。同一台机器、同一个网络，为什么对数据大小这么"挑剔"？这题一解就是一天，最后改到了 Rust 写的虚拟化层源码里。

一、背景速览：MTU / MSS / virtio 网卡，三块拼图

在讲排障前，先建立三个概念——没有它们，后面的现象完全不可理解。

拼图一：MTU 与 MSS。MTU（Maximum Transmission Unit）是链路层能承载的最大帧。TCP 发送数据时要按 MSS（最大分段大小）切段，经典公式 MSS = MTU − 40（20 字节 IPv4 头 + 20 字节 TCP 头）。发送端通告的 MSS 来自自己网卡的 MTU。比如 MTU 1500 的网卡通告 MSS 1460。

拼图二：黑洞的机制。如果数据链路某一段的 MTU 比发送端通告的小，那么"太大的包"有两种命运：要么沿途设备发回 ICMP "Packet Too Big" 让发送端降速重发（健康），要么被静默丢弃（黑洞）。丢弃没有任何反馈，发送端还以为包在路上，于是表现为超时/截断——这就是"黑洞"名字的由来。

拼图三：沙箱的网卡是 virtio-net。沙箱是一台 PVM 虚拟机，它的 eth0 是虚拟网卡（virtio-net），由 hypervisor（VMM）创建。virtio-net 有一个特性位 VIRTIO_NET_F_MTU：宿主机可以通过它告诉 guest 内核"你该用多大的 MTU"。也就是说，guest 的 MTU 不是 guest 自己定的，而是宿主机传进去的。这正是这次排障的突破口。

二、问题：按数据大小"挑食"的网络

三个观察，互相印证：

$ curl -s -o /dev/null -w '%{http_code}' http://www.baidu.com 200 # HTTP 正常 $ curl -k -s -o /dev/null -m 15 https://www.baidu.com 000 # HTTPS 握手超时 $ python3 -c 'import socket; socket.create_connection(("www.baidu.com", 443))' # 成功 —— TCP 层是通的！

TCP 能连上（SYN/SYN-ACK 都是小包），说明不是路由不通；HTTP 能通（GET 响应体通常只有几 KB，被切分成若干 ≤1460 字节的段）；唯独 HTTPS 挂——TLS 握手里，ServerHello 之后紧跟的证书链是一大坨数据，动辄几 KB。为什么大段数据过不去？

再补一刀：下载 1MB 文件，只收到约 228KB 就断了。一个精确的"截断点"，强烈暗示超过某一大小的数据被稳定地丢弃。

三、根因：1500 与 1450 之间的"静默黑洞"

把这条链路上每一段的 MTU 都量一遍，答案就出来了：

节点MTU可承载 TCP 载荷上限
沙箱 guest eth0（virtio-net）1500（打包默认 mvm_mtu=1500）1460（通告 MSS）
宿主机 tap（cube-dev / z172.16.x.y）15001460
cube-node Pod eth0（Calico VXLAN）14501410

Calico 的 VXLAN 模式要在数据帧外包一层 50 字节的 VXLAN/UDP/IP 头，所以 Pod 网络的 MTU 是 1450。于是黑洞出现：

guest 按 MTU 1500 通告 MSS=1460，但数据面最多承载 1410 字节载荷。回程任何长度在 1411~1460 之间的 TCP 段，超过 Pod MTU，被 Calico 数据面静默丢弃——没有任何 ICMP 通知。

为什么会"半通半不通"？因为 TCP 丢包后会重传，重传的段还是 1460 大小——永远超限，永远重传，永远丢。HTTP 响应小、段少，恰好没撞上阈值；TLS 证书和大文件下载，段段 1460，撞个正着。

上排是问题链路：guest 通告 MSS 1460，超过 Pod 数据面 1410 的上限；下排是修复：guest MTU 对齐 1450，MSS 1410 恰好不越界。

四、第一层修复：让 guest 的 MTU 对齐 Pod 网络

修法很直白——把沙箱的 MTU 从 1500 改成 1450。难的是"改哪里"。首先要让宿主侧的 tap 设备用 1450，这由 Helm 配置链控制：

# values.yaml 新增参数（默认 0 = 用打包默认值） cubeNode: network: mtu: 1450

这个值经 _helpers.tpl 的 cube.nodeComponentCommonEnv 变成环境变量 CUBE_SANDBOX_NETWORK_MTU，再由 cube-node-entrypoint.sh（以及单组件部署的 component-entrypoint.sh）在启动时用 sed 把 Cubelet config.toml 里的 mvm_mtu 打补丁——并做了整型校验防止注入：

if [[ -n "${CUBE_SANDBOX_NETWORK_MTU:-}" && "${CUBE_SANDBOX_NETWORK_MTU}" != "0" ]]; then [[ "${CUBE_SANDBOX_NETWORK_MTU}" =~ ^[0-9]+$ ]] || fail "CUBE_SANDBOX_NETWORK_MTU must be a non-negative integer" sed -i "s/mvm_mtu = [0-9]\+/mvm_mtu = ${CUBE_SANDBOX_NETWORK_MTU}/" "${CUBELET_CONFIG}" fi

改完发现：宿主机侧全部对了——cube-dev、z172.16.x.y 的 MTU 都是 1450，network-agent 传给 Cubelet 的 Interface.MTU=1450 也没错。但 guest 里的 eth0 依然是 1500。信息在"进入虚拟机"这一步断了——而这正是背景速览里拼图三说的：guest MTU 由宿主机通过 virtio-net 传进去，现在没人传。

五、第二层修复：CubeShim 透传 MTU 到虚拟机

链路是：Cubelet 把接口信息（含 MTU）发给 CubeShim，CubeShim 构造 NetConfig 交给 VMM（hypervisor），VMM 再通过 virtio-net 的 VIRTIO_NET_F_MTU 通知 guest。查源码发现，CubeShim 的 add_nets 构造 NetConfig 时根本没拷贝 MTU 字段：

// CubeShim/shim/src/hypervisor/config.rs — 修复前 let mut nc: NetConfig = NetConfig { id: Some(...), tap: n.name.clone(), ..Default::default() }; // nc.mtu 从未被赋值 → None

修复是在两处把 MTU 显式传下去，并利用 VIRTIO_NET_F_MTU 让 guest 内核应用通告值：

// 修复后：add_nets（新创建路径） if n.mtu > 0 { nc.mtu = Some(n.mtu as u16); // VIRTIO_NET_F_MTU 让 guest 应用该 MTU } // 修复后：restore_nets_config（快照恢复路径，CubeShim/shim/src/common/utils.rs） if n.mtu > 0 { net_config.mtu = Some(n.mtu as u16); }

还有第三处：hypervisor/vmm/src/config.rs 的 update_nets。它负责在 VM 状态更新（快照恢复）时把新的网络配置合并进 VM 的 NetConfig，但原来只复制了 tap 和 rate_limiter_config，把 MTU 丢了。这次一并补上：

// update_nets 修复：新增 mtu_map，恢复时按网卡 id 回填 MTU let mut mtu_map: HashMap<String, Option<u16>> = HashMap::default(); // ...遍历 net_cfgs 收集 mtu ... for net in nets.iter_mut() { if let Some(mtu) = mtu_map.get(&id.clone()) { net.mtu = *mtu; } }

这里"快照恢复路径"为什么要单独修？因为沙箱大多从模板快照恢复，恢复时走的是 update_nets 合并配置——如果它丢 MTU，恢复出来的 guest 还是 1500。三条路径（新建 + 快照恢复 + 恢复合并）都得补，缺一条都会让 guest MTU 回到 1500。

六、第三层：在 64_host 编译并替换 shim 二进制

改动在源码，生效得重新编译。64_host 上先装齐工具链：

apt-get install -y build-essential libseccomp-dev libcap-ng-dev # 首次编译曾报：error: linking with 'cc' failed: cannot find -lseccomp / -lcap-ng
cd /opt/cube-build/CubeShim cargo build --release # 产出 target/release/{containerd-shim-cube-rs, cube-runtime}

然后替换节点上的二进制并重启 cubelet 使其加载新 shim：

cp -f /opt/cube-build/CubeShim/target/release/{containerd-shim-cube-rs,cube-runtime} \ /usr/local/services/cubetoolbox/cube-shim/bin/ kubectl -n cube-system rollout restart ds/cube-node

七、第四层（关键）：为什么模板必须重建

代码改了、shim 换了，可新沙箱的 eth0 还是 1500。原因在模板创建机制：模板创建流程会先起一个"build 沙箱"跑构建，然后把它的磁盘 + 内存做成快照（AppSnapshot）。如果 build 沙箱是从旧模板的快照恢复的，那么 guest 启动走的是"快照恢复"路径——而这条路径的 MTU 透传正是我们刚在 update_nets 里修的那一环，旧二进制没有这个修复。

于是修复后的正确做法是：重新建一个模板（不带 --node 让 CubeMaster 自动选健康节点），保证 build 沙箱冷启动，让新 shim 的 MTU 透传完整走一遍。重建后验证：

$ ip link show eth0 # mtu 1450 ✓ $ curl -k https://www.baidu.com # 200，TLS 握手正常 ✓ $ curl -O http://.../1MB.zip # 完整下载 ✓

八、权衡：为什么"黑洞"如此难查

常见排查手段为何失效
ping / TCP connect小包都能过，黑洞只吞 1411~1460 的大段
看各段 MTU每一段看起来都"正常"（1500/1450 都是合法值），差异藏在跨段处
路由跟踪黑洞不产生 ICMP，无从报告
tcpdump 抓包能看到 SACK 重传、部分段到达——需要很强的前后对照才能定位

而修复本身也是三层：配置层（helm mtu 参数）解决"告诉宿主机用多少"，CubeShim/VMM 层解决"把 MTU 传进 guest"，模板层解决"让 build 沙箱冷启动走新代码"。任何一层缺失，guest 的 MTU 都还是 1500。

一句话带走 MTU 黑洞的根因是 guest 通告 MSS 1460 而数据面只承载 1410；修复要贯穿三层——Helm 配置 mvm_mtu、CubeShim 的 add_nets / restore_nets_config / update_nets 透传 MTU（VIRTIO_NET_F_MTU）、重建模板让 build 沙箱冷启动走新代码。
