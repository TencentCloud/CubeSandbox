先看懂一张地图：CubeSandbox 全景速览

这一篇不是排障，是为后面四篇排障铺路。如果你第一次接触 CubeSandbox，请先花十分钟读完这篇——它回答三个问题：一个"沙箱"到底是什么、SDK 一行代码背后发生了什么、那么多组件各管什么。有了这张地图，后面每篇排障你都能立刻定位"问题出在地图的哪个角落"。

一、一个"沙箱"，到底是什么

在 CubeSandbox 里，沙箱（Sandbox）并不是 Docker 容器，而是一台真正的轻量虚拟机（MicroVM）。它有自己的 Linux 内核、自己的文件系统（rootfs）、自己的 IP。你调用 SDK 创建沙箱，实际上是在一台宿主机上启动了一台新的虚拟机。

这台虚拟机用 PVM（Pagetable-based Virtual Machine，页表虚拟化）运行——不需要 KVM 那样的硬件辅助虚拟化，纯软件分页，所以对宿主机没有"必须开 KVM"的要求。但这也意味着：你创建沙箱的每一秒，都有真实的 CPU、内存、磁盘被一台完整的操作系统占着。

虚拟机里常驻一个叫 envd 的进程，监听固定的 49983 端口。它相当于沙箱的"操作系统代理"：你的命令执行、文件读写、进程管理等，最终都是 envd 在虚拟机里替你完成的。

那"秒开"是怎么做到的？
靠模板快照。见下一节——这是理解整个系统最重要的概念。

二、模板：秒开沙箱的秘诀

从零启动一台 Linux 虚拟机需要几十秒（加载内核、初始化系统）。CubeSandbox 的沙箱能"秒开"，秘密在 模板（Template）。

模板创建过程（cubemastercli template create-from-image）大致是：

① 拉取一个 OCI 镜像（Docker 镜像） ② 把镜像转换为一个 ext4 磁盘镜像（rootfs） ③ 用这个 rootfs 启动一台"build 沙箱"，执行镜像里预设的初始化脚本 ④ 把这台沙箱的磁盘 + 内存 打成一份快照（AppSnapshot），保存为模板

之后每次创建沙箱，都不是从零启动，而是从模板快照恢复——把快照里的磁盘和内存"克隆"出来，一台"已经初始化好、正在运行"的虚拟机立刻出现在眼前。这就是秒开的原理。

代价是：模板是"死"的。rootfs 里的配置文件（比如 /etc/resolv.conf）在快照里就定型了，运行时很难再改。这个"静态"特性，会在排障链二（DNS）里坑你一次。

另一个关键点：模板创建时通过 --expose-port 声明"这个沙箱对外暴露哪些端口"。端口没声明，外界就永远连不进来——这是排障链一的伏笔。

三、SDK 一行代码，背后有两条完全不同的路

用 Python SDK 写一个最小示例：

sb = Sandbox.create(template=tpl) # ① 创建沙箱 sb.commands.run("echo hello") # ② 执行命令 sb.get_info() # ③ 查询状态

这三行代码，走的是两条互不相干的路：

操作打给谁做什么
①③ 创建 / 查状态CubeMaster 控制面（CubeAPI，HTTP :3000）调度、分配资源、记录元数据
② 执行命令CubeProxy 数据面（HTTP :80）路由到沙箱内 envd，实时往返

这个区分极其重要：创建沙箱的"开关"和沙箱内命令的"水管"是两套系统。一个出问题不影响另一个。排障链一就是两条路之间"端口没对上"。

四、组件全景：谁在管什么

把整个系统摊开，分成"控制面"和"节点数据面"两层。控制面是大脑，决定"创建哪个沙箱、什么时候暂停"；节点数据面是手脚，真的去启动虚拟机、转发流量。

层次组件一句话职责
控制面CubeMaster / CubeAPISDK 的入口；调度沙箱落到哪台节点、管理模板、处理 pause/resume
cube-lifecycle-manager（CLM）自动暂停/恢复的协调中枢：扫描闲置沙箱、状态对账
CubeProxy反向代理，把 SDK 的"命令请求"路由到具体沙箱；维护沙箱状态门禁
Redis / MySQLRedis：元数据、事件流、服务注册表；MySQL：持久化业务数据
节点数据面cubelet每台节点上的代理，管理本节点沙箱生命周期（类似 K8s 的 kubelet）
CubeShim + VMMcontainerd shim 与轻量虚拟机监控器，真正把虚拟机拉起来 / 暂停
CubeNet（CubeVS）eBPF 网络数据面：沙箱出向 SNAT、网络策略、DNS 学习
network-agent管理虚拟网卡（tap 设备）、给沙箱分配 IP、配置 MTU
本篇之后的所有排障，都能在这张图上定位：链一在 CubeProxy 路由，链二在 CubeNet 策略，链三在 CubeShim/VMM 网络配置，链四在 CubeProxy↔CLM↔Redis 的注册链路。

五、一次命令执行，完整旅程

把第 ② 行 commands.run() 展开，它实际走了这样一段路：

SDK └─ HTTP 请求，Host 头 = <sandbox_id>-49983.cube.app # 虚拟域名，端口固定 49983 └─ 到达 CubeProxy └─ Lua 解析 Host：沙箱 ID = xxx，目标端口 = 49983 └─ 查 Redis 代理映射 …sandbox:proxy:<id>：49983 → 宿主端口 └─ 转发到节点上的宿主端口 └─ 经网络数据面进入沙箱的虚拟网卡 └─ 沙箱内 envd（:49983）接收，执行命令，返回结果

注意 Redis 代理映射这一步：沙箱在哪个节点、以哪个宿主端口暴露 49983，都记录在 Redis 的一个 hash 里。这一步查不到，命令就永远到达不了沙箱——排障链一正是栽在这里。

六、生命周期：沙箱会"睡觉"

沙箱有状态：running（运行中）、paused（暂停）、killed（已销毁）。暂停（pause）不是关停，而是把虚拟机内存写盘成快照、释放 CPU/内存，需要时再恢复（resume）——这天然复用了模板的秒开机制。

谁触发暂停？用户手动调 sb.pause()，或者设置 lifecycle={"on_timeout":"pause","auto_resume":True} 后由 CLM 自动判定"空闲超时"而暂停。谁触发恢复？用户请求到达时，CubeProxy 的"门禁"发现沙箱是 paused，会内部通知 CLM 把它唤醒。这套"睡/醒"的协作链条，就是排障链四的主战场。

七、本系列排障的地图坐标

排障现象一句话根因在地图的哪
01 · envd 端口建沙箱成功，命令 ConnectExceptionCubeProxy → Redis 代理映射：模板没暴露 49983
02 · 沙箱 DNS公网域名解析失败CubeNet eBPF 策略默认拒绝私网段（含 CoreDNS）
03 · MTU 黑洞HTTP 通、HTTPS 超时、大文件截断CubeShim/VMM 没把 MTU 传进虚拟机
04 · auto_resume 504自动暂停正常，自动恢复 504CubeProxy 心跳写向过期 Redis IP → CLM 发现不到代理
一句话带走 记住三件事就够：沙箱是一台由模板快照秒开的 PVM 虚拟机；创建走 CubeMaster、命令走 CubeProxy 两条独立链路；运行中沙箱还会被 CLM 自动暂停和恢复。后面每篇排障都在这三句话的延长线上。
