CUBESANDBOX · 部署排障 01 / 05

沙箱建好了，命令却一条都跑不了

部署完 CubeSandbox，第一件事自然是拿 SDK 试试手。`Sandbox.create()` 秒回、沙箱 ID 都拿到了——可紧接着的 `commands.run('echo hi')`，直接抛出一个干巴巴的 `ConnectException`。创建成功但命令全挂，问题出在"创建"和"命令"这两条完全不同的路上。

一、背景速览：先分清"创建"和"命令"是两条路

如果你还没读前置篇，这里先补一块最重要的地图：CubeSandbox 的 SDK 调用被刻意拆成了两条互不相干的网络路径。

操作走哪条路依赖什么
Sandbox.create() / get_info()CubeMaster 控制面（CubeAPI，HTTP :3000）模板存在、有节点能调度
commands.run() / files.*CubeProxy 数据面（HTTP :80）沙箱内 envd 端口（49983）被"暴露"

为什么拆开？因为这是两种完全不同的流量：创建是低频控制操作，命令是高频实时数据流。拆开后，控制面故障不影响已运行沙箱的命令通道，反之亦然。代价是：排障时必须先搞清楚当前错误是哪条路报的。

二、机制之一：命令通道 = "虚拟域名 + 动态后端"

命令请求长什么样？SDK 在 cubesandbox/_commands.py 里，用 e2b_connect 库发一个 gRPC-streaming 请求，目标是沙箱内 envd 进程监听的固定端口 49983。关键在请求的 Host 头：

ENVD_PORT = 49983 # 沙箱内 envd 的固定端口，写死在 SDK 里 def _envd_rpc_base_url_and_headers(sandbox): ... headers["Host"] = sandbox.get_host(ENVD_PORT) # → Host: <sandbox_id>-49983.cube.app return f"http://{proxy_node_ip}:{proxy_port}", headers

这个 Host 是虚拟域名：格式固定为 <sandbox_id>-<端口>.cube.app。请求到达 CubeProxy 后，OpenResty 的 Lua 从 Host 里解出 sandbox_id 和 49983，然后查 Redis 里的一份代理映射（HSET 结构，key 类似 …sandbox:proxy:<id>），拿到这个沙箱"在哪个节点、以哪个宿主端口承载 49983"：

# Redis 里的代理映射（HSET） HostIP = 192.168.4.64 # 沙箱所在节点 SandboxIP = 172.16.x.y # 沙箱自己的 IP "49983" = 33021 # 节点上暴露 49983 的宿主端口

然后 CubeProxy 把请求转发到 HostIP:宿主端口，再经网络数据面进入沙箱，最终 envd 收到并执行。

那 Redis 映射里"有哪些端口"是谁决定的？
是模板。模板创建时用 --expose-port 声明了"这个沙箱对外暴露哪些容器端口"。沙箱是模板的克隆体，模板没暴露的端口，代理映射里就永远没有。

三、问题：建沙箱成功，命令却 ConnectException

用脚本复现：

sb = Sandbox.create(template=tpl, timeout=120) # 返回 sandbox_id，正常 ec, out, err = sb.commands.run("echo hello") # 抛 ConnectException # e2b_connect.client.ConnectException: (<Code.unknown: 'unknown'>, '')

ConnectException 没有 HTTP 状态码——不是 404、不是 500，是连接层的失败："TCP 握手根本没成功"。创建走 CubeMaster 成功了，说明控制面没问题；命令走 CubeProxy，问题必然出在命令这条链路的某个环节。

SDK 请求 → CubeProxy → Redis 查映射 → 映射里没有 49983 → 后端解析失败 → ConnectException。修复点在"模板"这一源头。

四、根因：模板暴露的端口，不是 49983

第一次建模板时，命令是：

cubemastercli template create-from-image --image <image> --expose-port 8000

容器端口 8000 被写进模板元数据。于是沙箱创建后，Redis 代理映射里只有 HostIP / SandboxIP / "8000"——没有 49983。当 SDK 的请求带着 Host: <sid>-49983.cube.app 到达 CubeProxy 时，Lua 侧 sandbox_backend.lua 的 resolve_backend(ins_id, "49983") 查表，metadata_map["49983"] 是 nil——没有宿主端口，转发无门，连接直接失败。

为什么之前用 8000？因为模板镜像本身是个 Web 服务镜像，端口是 8000。但对 CubeSandbox 来说，命令执行要求模板必须暴露 envd 端口 49983——这是 SDK 与沙箱之间的"内部契约"，和镜像本身的业务端口无关。建模板时只想着业务端口，漏了内部端口，是最容易踩的坑。

五、修复：重建模板，暴露 49983

重建模板：

cubemastercli template create-from-image --image <image> \ --expose-port 49983 --writable-layer-size 20Gi

两个参数都值得说明。--expose-port 49983 是本次的关键；而 --writable-layer-size 20Gi 是 CLI 校验里的一个"必填项"——缺了它命令直接报 writable-layer-size is required，属于不算友好的细节。重建后重新创建沙箱，命令执行立即恢复。

六、权衡：为什么是"端口即契约"

这套"模板声明暴露端口 + Host 虚拟域名路由"的设计，本质是把暴露面显式化：沙箱默认对网络封闭，只有模板声明的端口才写入 Redis 映射、才可能被代理路由到。

好处代价
安全：一个模板只开一个端口，其余全屏蔽排障直觉陷阱：错端口报"连接失败"，无状态码可查
每个端口都是显式声明的"契约"创建与命令两套链路，配置来源（模板元数据）不同，端口不匹配时错误只浮现在命令层

记住这张对照表——排障链二（DNS）还会用到"模板元数据决定运行行为"这个心智。

一句话带走 命令执行走的是"Host 虚拟域名 → CubeProxy → Redis 端口映射"的独立链路；模板创建时漏了 --expose-port 49983，映射表里没有 envd 端口，命令请求自然无处可去。
