CUBESANDBOX · 部署排障 04 / 05

沙箱自己睡了，却没人能把它叫醒——auto_resume 504 之谜

验证脚本的最后一项：创建一个 `lifecycle={"on_timeout":"pause","auto_resume":True}` 的沙箱，等 35 秒让它自动睡觉，再发命令把它叫醒。暂停一切正常，状态也显示 `paused`——可叫醒的命令全是 504，恢复后状态还是 `paused`。自动暂停活了，自动恢复却整条链路是死的。

一、背景速览：沙箱的"睡眠"机制

CubeSandbox 有一个省钱的杀手锏：沙箱闲置时自动"睡觉"。这需要先讲清楚几个概念。

① 暂停不是关机。沙箱有状态：running（运行中）、paused（已暂停）、killed（已销毁）。暂停（pause）是把虚拟机的内存写盘成快照、释放 CPU/内存，但磁盘镜像保留——需要时从快照恢复，几秒内回到暂停前的状态，用户无感。这和前置篇里"模板秒开"是同一个机制。

② 谁决定它睡觉？用户可以在创建沙箱时声明生命周期策略：lifecycle={"on_timeout":"pause","auto_resume":True}，含义是"空闲超时自动暂停；收到请求自动恢复"。真正执行这个策略的是 CLM（cube-lifecycle-manager）——一个独立部署的控制面组件，它扫描闲置沙箱、执行暂停、响应恢复请求。

③ 用户请求来了，怎么把睡着的沙箱叫醒？这是本篇文章的核心：用户请求先到达 CubeProxy（数据面）。CubeProxy 内部维护一个状态字典 cube_sandbox_state，记录每个沙箱当前是 running 还是 paused。请求到达时，门禁（gate）查字典：如果是 paused，就内部回调 CLM 的 /internal/resume 把沙箱唤醒，再继续转发。问题是——CubeProxy 的字典是谁填的？它怎么知道沙箱被暂停了？

二、机制：自动恢复的四段接力

答案是一套四段式的"接力"，每一段都依赖上一段：

接力段实现作用
① 代理注册CubeProxy proxy_registry.lua 心跳写 Redis让 CLM 知道"有哪些 CubeProxy 活着、admin 端口在哪"
② 服务发现CLM discovery.RedisDiscovery 扫描心跳构建可推送的 proxy 端点列表（fleet）
③ 状态推送CLM proxypush.Client.broadcast → POST /admin/state把 paused/running 写进每个 CubeProxy 的共享字典 cube_sandbox_state
④ 请求门禁CubeProxy sandbox_state.lua gate请求到达时查字典：paused → 内部回调 CLM /internal/resume 叫醒沙箱

把这条链路想成"对讲机调度"：CubeProxy 每隔几秒通过对讲机喊一声"我在，我的 admin 端口是 X"（①）；CLM 听着对讲机记下所有在场的代理（②）；CLM 有状态变化时就拨号通知每个在场的代理"沙箱 A 暂停了"（③）；代理在请求到来时查自己的记录本决定要不要唤醒沙箱（④）。只要 ① 的心跳断了，②③④ 全部失效。

②③④ 的正常运转完全依赖 ① 的心跳成功写进 Redis；心跳断了，后面全部静默失效。

三、问题：一半活着，一半死着

# 验证脚本步骤 10 等待 35 秒触发 auto_pause... [PASS] 超时后状态为 paused（当前=paused） 发送请求触发 auto_resume... (attempt 1 failed: 504 Gateway Time-out) # openresty 返回 (attempt 2 failed: 504 Gateway Time-out) (attempt 3 failed: 504 Gateway Time-out) [FAIL] 自动恢复后命令执行成功

最有意思的细节：手动单独复现（新建一个同样的 auto_pause 沙箱）一切正常——暂停、恢复、命令，全都对。功能本身没坏，是这个特定环境下的某条链路悄悄断了。

四、排查：从 504 一路追到 Redis 心跳

504 来自 openresty 的"upstream 超时"。逐层取证，用排除法收窄——每一步都在缩小嫌疑范围：

第一刀：CubeProxy error.log 查 gate。gate 一旦判定沙箱是 paused，就会打日志并回调 CLM。结果：该沙箱在 error.log 里 0 条记录。说明 gate 根本没走 resume 分支——字典里没有这个沙箱的 paused 状态。嫌疑：状态字典是空的。

第二刀：CLM 日志查 resume 请求。CLM 收到 /internal/resume 必打 resume request received。结果：没有。CLM 根本没收到叫醒请求。连起来就是：gate 放行了请求 → 请求打到已暂停的沙箱后端 → 无响应 30 秒 → 504。两刀下去，问题锁定在"gate 为什么放行"。

第三刀：为什么会放行？gate 查的是 worker 内共享字典 cube_sandbox_state，这个字典由 CLM 经 /admin/state 写入。字典空 → 没有 paused → gate 放行。那 CLM 推了没有？——推了，但推给了"空列表"。

第四刀（根因）：Redis 里的注册表。CLM 的 broadcast 每次推送前都从 fleet 取端点列表；fleet 来自 Redis 服务发现；而 Redis 里的注册表由 CubeProxy 心跳维护。查 Redis：

$ redis-cli KEYS "cube:v1:shared:cube_proxy:*" (empty array) # 一个键都没有！

CubeProxy 的心跳从来没写进过这个 Redis。fleet 为空 → broadcast 遍历空列表 → 静默跳过（只有 Debug 日志）→ 字典永不填充 → gate 永远放行 → 504。至此，根因浮出水面：心跳为什么写不进去？

五、根因：一条"渲染时固化的 IP"

CubeProxy 心跳要连的 Redis 地址，来自 Helm chart 在 proxy.yaml 里渲染出的环境变量。原逻辑：内置 Redis 是 headless Service + StatefulSet，chart 在渲染时用 lookup 读 Endpoints，把当时 Redis Pod 的 IP 写死进环境变量：

# 修复前：lookup 固化 Endpoints IP {{- $redisEps := lookup "v1" "Endpoints" ... }} {{- $redisRegistryHost = (index $subset.addresses 0).ip }} # → 渲染结果：CUBE_PROXY_REGISTRY_REDIS_HOST=10.60.235.237

而 proxy_registry.lua 跑在 ngx.timer 里，cosocket 没有 nginx resolver，只能用 IP 直连。这个 IP 是 Helm 渲染那一刻的 Redis Pod IP——之后 Redis Pod 重建，IP 变成 10.60.235.240，但 cube-proxy 的环境变量是静态的，心跳就永远写向那个已死掉的 10.60.235.237:6379。

为什么这么难发现？
三个"静默"叠在一起：心跳失败只有 proxy 的 ERR 日志（在容器内文件里，不随 stdout 出）；fleet 为空时 broadcast 只打 Debug 不告警；gate 字典缺失时按"未加入生命周期"处理、放行请求。每一环都优雅地失败了，最后只有一个没有状态码意义的 504 浮出水面。

六、修复：让地址"活"起来

修法是把"固化 IP"换成"可解析的主机名"——headless Service 的 StatefulSet Pod DNS 名 cube-redis-0.cube-redis.cube-system.svc.cluster.local 永远指向当前存活的 Pod，由入口脚本在启动时解析成 IP：

# chart 修复：headless 分支改用 Pod DNS 名 {{- $redisRegistryHost = printf "%s-0.%s.%s.svc.%s" ... }}
# cube-proxy-entrypoint.sh：启动时 getent 解析成当前 IP if [ -n "${CUBE_PROXY_REGISTRY_REDIS_HOST:-}" ]; then case "${CUBE_PROXY_REGISTRY_REDIS_HOST}" in *[!0-9.]* ) # 非纯 IP 才解析 resolved="$(getent ahostsv4 "${CUBE_PROXY_REGISTRY_REDIS_HOST}" | awk 'NR==1 {print $1}')" [ -n "${resolved}" ] && export CUBE_PROXY_REGISTRY_REDIS_HOST="${resolved}" ;; esac fi

这里"为什么不直接用 nginx resolver 在 Lua 里解析？"因为 proxy_registry.lua 跑在 ngx.timer 定时器里，Lua cosocket 没有 nginx resolver 可用，只能连一个具体的 IP。所以退而求其次：入口脚本（bash，有完整 DNS 能力）在启动时把主机名解析成当前 IP，再把解析结果交给 Lua。各用各的时机，各补各的短板。

现网立即修复，一条命令滚动更新：

kubectl set env deploy/cube-proxy -n cube-system \ CUBE_PROXY_REGISTRY_REDIS_HOST=cube-redis-0.cube-redis.cube-system.svc.cluster.local

七、验证：链路重新点亮

更新后，四个关键证据先后出现：

# ① Redis 有了注册表和心跳 cube:v1:shared:cube_proxy:heartbeat cube:v1:shared:cube_proxy:registry # ② CLM 发现新代理并完成对账 discovery: proxy joined proxy_id=cube-proxy-6994fd99bb-7ws2z replay begin entries=3 replay done pushed:3, failed:0 # ③ 验证脚本 结果: 34/34 通过, 0 失败 # auto_resume 恢复如初

八、权衡：为什么"渲染时固化"会失效

维度固化 IP可解析主机名（本次修复）
渲染期正确性✓ 当时一定可达✓ DNS 解析当前值
运行期持久性✗ Pod 重建即失效✓ 永远指向存活 Pod
对运行环境的假设无（纯 IP）需有 DNS + 启动期解析（entrypoint 已实现）
失败可见性静默（仅 Debug）解析失败会立即暴露在启动日志

教训也清楚：用 lookup 把集群内地址固化进 env，等于把"运行时才会变的东西"在"渲染时"定格。headless Service + StatefulSet 的 Pod DNS 名是天然稳定的标识，而 getent 在入口脚本解析，正好补齐了 Lua cosocket 无 resolver 的短板——各用各的时机，各补各的缺口。

一句话带走 auto_resume 504 的根因是 CubeProxy 心跳写向了 Helm 渲染时固化的过期 Redis Pod IP，导致 CLM 服务发现 fleet 为空、状态字典永不填充、gate 永远放行；改成 StatefulSet Pod DNS 名 + 入口脚本启动期解析后，四段接力重新点亮。
